One thing changed this week, and what the landings show

Build a package in one command

Build your first NAOMS package is a tutorial. One command, naoms package init, scaffolds an app with a manifest, a screen and tests, and the post walks through writing one record and seeing it in the app's own window.

What the week's landings say

These are described only as far as the landing subjects state them. Where a subject says a change is on a branch or not yet working, that is how it is reported here.

  • Calls. Subjects describe a call media frame without a valid signature being dropped on receive and never sent (recorded as an owner ruling), a call's ephemeral adverts being admitted only from an authenticated roster member, one-to-one call verifier material being refused when it has no authenticated author, and each device asking its own person for consent when a call reaches three people.
  • Hives. An unset hive access policy is described as failing closed, with self-join allowed only for hives marked open, and a per-hive public key being published on the join path.
  • Packages and the store. Package search is described as returning one row per package id, a package with no name being refused instead of indexed as "unknown", and the storefront's install being described as obtaining the full permission gate or refusing. The marketplace storefront landings are branch work, and one subject says plainly that the window size does not yet work.
  • Vault and browser. The open Vault Secrets list is described as no longer rendering an older load over a newer one, and the route that serves package files is described as scoped so a peer's payload cannot run script under it.

Where the week's landings clustered

This is landing-subject frequency: a read of the subjects of the week's first-parent landings onto main, grouped by theme. It is not the per-commit file union that earlier dispatches used, and it says how often a theme appears in subjects, not how large the work was.

Themes, roughly from most to least frequent: calls, vault, packages, store, hives, Rust and specification work (a trust-task registry and gate slice, and quorum member-signature rules on shared chains, both described in subjects as work in progress), install, and browser. A large share of the subjects belong to a few long-running design-and-align branches that merged main into themselves many times, which inflates the count of landings without meaning the same number of separate changes.

An honest note on this week's pace

This is the highest-count week in the run so far, and 09-27 alone carries 1,869 commits. As the week before, a lot of that is branch work and repeated merges of main into long-lived branches reaching the shared line, so the figure measures landing activity, not features delivered. Nothing here should be read as a claim that the gated or in-progress items above are live: the Rust, trust-task and storefront work is specification and build in progress.

How the figures are counted. Commits are counted by committer date, UTC, over the post-rewrite history (the 1797 package-extraction rewrite rewrote git history), so they do not chain to the pre-September published dispatches; a different counting method would read differently.

What would prove this week wrong

  • The calls and hives descriptions come from landing subjects. A subject states intent; it is not proof the behaviour holds between two real devices.
  • The tutorial's walk-through is one run on the scaffold as it stood on that day. A later change to the scaffold command could make the steps differ.
  • The cluster paragraph is subject frequency. Branches that merge main into themselves repeatedly push a theme up the list without adding separate work.
  • These figures do not chain to earlier dispatches. Read each week's numbers on their own.
