How Uninstalling an App Frees Only the Files Nobody Else Uses

Two packages can ship the same file, so deleting one package must not delete the file out from under the other. NAOMS keeps a small ledger of who holds what, and tells you honestly what it did

Product Architect free November 19, 2026·4 min read
TL;DR A package is made of files, and files are stored by what they contain, so one stored copy can serve several packages. This is how NAOMS counts the holders of each file, removes a file only when the last holder leaves, reports four honest outcomes instead of a bare 'done', and rebuilds the ledger from your history if it is ever lost.

Install two apps that both bundle the same speech model. It is a big file, and you would not want two copies on disk. Now uninstall one app. What should happen to the model?

Delete it, and the other app breaks. Keep it forever, and uninstalling never gives your disk space back. The right answer is: remove it only when nobody else needs it. NAOMS gets there with a small ledger, and the interesting part is what the ledger refuses to hide.

One file, many owners

NAOMS stores files by their contents, not by their names. Two packages that contain byte-for-byte the same file end up pointing at a single stored copy. That is efficient, but it means a file has no single owner. Ownership has to be written down somewhere else.

So when a package is installed, NAOMS adds one row to a local table for every file it stored. Each row says: this file, held by this package, at this version, as one of three kinds (the package itself, a model, or an ordinary file in it). Adding the same row twice changes nothing, so reinstalling or replaying an install is safe.

Think of it as a library sign-out sheet. The book stays on the shelf as long as anyone's name is on it.

What uninstall does, in order

flowchart TD
  A[Uninstall is recorded in your history] --> B[Remove this package's rows from the ledger]
  B --> C{Does any other package still hold the file?}
  C -- yes --> D[Keep the file, note who still holds it]
  C -- no --> E{Can the file store be reached right now?}
  E -- no --> F[Note that removal is waiting]
  E -- yes --> G[Erase the file]
  G --> H[Note: removed, not found, or failed]

First the uninstall itself is written to your history, so the fact that you removed the package is durable. Then the ledger is updated, and this order matters. The rows for that package and version are deleted, always. Bookkeeping never gets stuck waiting for the slow part.

The slow part is erasing bytes from disk. That work happens outside the step that writes your history, so a slow disk can never hold up recording the uninstall.

For each distinct file the package held, NAOMS then asks one question: is anyone else's name still on it? If yes, the file stays, and an audit note records that it was kept and how many holders remain. Only a file with no holders left is eligible for erasure. Importantly, the erase is attempted once per distinct file, not once per row, so a file listed under two kinds is not erased twice.

Four honest outcomes

When a file has no holders left, one of four things happens, and each leaves its own audit note and its own count:

  • Removed. The bytes were found and erased.
  • Not here. The file was not on this machine. That is normal when another device or a cache holds it instead.
  • Waiting. The file store was not available at that moment, so the removal is recorded as pending.
  • Failed. The attempt raised an error, and the error is logged.

The uninstall response reports all of these counts, along with how many ledger rows were released. You do not get a bare "uninstalled". You get what actually happened to the bytes. An alternative design, a periodic sweep that cleans up orphans later, was rejected for exactly this reason: the uninstall could not honestly say what it freed, because the freeing had not happened yet.

Erasing is built to fail safe

The erase itself does two things in a deliberate order. It first marks the file as deleted so that it stops being handed out to anyone who asks, including peers. Only then does it remove the stored copies. If a later step fails, the file is left intact so the removal can be retried, but it is already refused for serving in the meantime. A half-finished delete never leaves a file that you asked to remove still available to others.

The ledger can be lost and rebuilt

The ledger is local bookkeeping. It is never written into your history or synced to other devices. Your history, which records every install and uninstall, is the durable truth, and the ledger is a view of it.

That is why the ledger can be rebuilt. Each time NAOMS starts, after the file transport is up, it runs a background sweep. It reads the install records that no later uninstall cancels, and re-adds the matching rows: the package file and any models downloaded for it. The sweep is safe to repeat, because adding an existing row does nothing, and it runs off to the side so a large history never delays startup.

If the file transport is not up when an uninstall arrives, the ledger still updates and the removal is reported as waiting. Nothing is silently dropped.

Why this shape

Two ideas run through it. First, a count of holders beats guesswork: the file goes away exactly when the last reason to keep it does. Second, the system says what it did. Every outcome is a named, counted, auditable event, not a quiet success.

The same pattern guards message attachments, where a ledger row is tied to a single message in a single conversation, so a message in one conversation can never release another conversation's file.
