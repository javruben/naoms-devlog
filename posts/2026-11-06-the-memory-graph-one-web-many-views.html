The Memory Graph: One Web, Many Views

The graph you query is not where truth lives. It is a projection of the signed chain, rebuilt by replay, and that changes how it works

Technology Architect free November 6, 2026·4 min read
TL;DR Nodes, edges, and queries are how you and your agents read your memory. But the graph is a materialized view of the signed event chain, not an independent store. This is how events become nodes, how reads work, and why you can wipe the graph and get it back.

When you open a contact, a task, or a hive in NAOMS, you are reading a graph. Nodes are things (a contact, a task, a hive). Edges are relationships between them (member of, has task). It feels like the database. It is not the source of truth, and understanding that one fact explains most of how it behaves.

The chain writes; the graph reads

Everything a person owns lives in one encrypted file on their own device. Inside it are two layers with different jobs. The chain is the append-only, signed log of events: the truth. The graph is a projection of that log, a materialized read surface that humans, the interface, and agents all query.

Every domain fact follows one road: event, then reducer, then materializer, then graph node. There is no general-purpose "write a node" door. Writers append a signed event, and the graph follows. The graph query tool exposed to agents is read-only for exactly this reason.

How an event becomes a node

Event payloads describe facts as linked data. The materializer groups statements by subject, reads the declared type to decide what kind of node it is, turns plain values into properties, and turns references to other things into edges. Each node remembers where it came from: who authored it, which chain, and which commit. Provenance edges point a node back to the commit that produced it and to the sharing domain it belongs to.

Two rules keep the projection honest:

  • Kinds do not silently change. If a node already exists as one kind and a write arrives claiming another, the system fails loudly instead of quietly keeping one and dropping the other's intent. A silent merge would be a silent mutation, which the honesty axiom forbids.
  • Materializers are append-only projectors. They never read their own output to decide what to write. That is what makes replay idempotent: run the same events twice and you get the same graph.

Why you can wipe it

Because the graph is derived, it can disappear and come back. Delete the nodes and edges, replay the chain through the materializers, and the same state emerges. That is the wholeness axiom in practice: the graph depends on nothing outside the chain. It is also the mystery axiom: hold the view lightly, let the log be the source.

Reading the web

Every read goes through a single query entry point, and it supports the shapes you would expect from a graph:

  • fetch by id, or by kind with property filters;
  • full-text search, and a hybrid mode that combines text with semantic similarity;
  • follow an edge one hop, or walk a path of several;
  • expand outward from a node to some depth, optionally limited to certain edge types;
  • rank by connectedness, or count values per facet.

This is the "many views." One web, queried as a list, a map, a timeline, or a search. Defaults are modest, so a bulk read has to ask for more explicitly. And the query surface is deliberately narrow: it answers about the graph and nothing else, because pretending to offer one unified view over every kind of storage would be a lie.

Who may see which node

Reads are scoped. A query carries the domains the caller is authorized to see, and each node's domain is established by an edge rather than a loose field. Beyond that, access depends on the caller's role, not on whether they happen to be on the owner's machine. The owner can read owner-only kinds. Other roles may read only concrete kinds explicitly classified as readable for them; a kind nobody has classified is unreadable by default.

Live views

Because the graph changes only when events materialize, the interface does not poll. A subscription registry routes each change to the queries it affects, re-runs them, and pushes only the differences to the client. A new subscriber starts from an ordinary query and then follows the stream.

Why this shape

Making the graph a projection means the chain stays the single authority, every node is traceable to a signed commit, and a corrupted or stale view is a rebuild rather than a disaster. It gives you rich, fast queries without letting the query layer become a second source of truth.
