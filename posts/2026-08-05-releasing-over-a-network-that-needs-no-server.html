Releasing Over a Network That Needs No Server

For most of this project's life, cutting a release meant one machine reaching out over SSH to build the others — a private network, a set of credentials, a hardcoded list of hosts. This week we cut that cord: a release tag now fans out its per-platform builds over our own peer-to-peer transport, with no SSH, no central host, and no host list to keep in sync.

Technology Architect free August 5, 2026·5 min read·distribution
TL;DR A system that claims to need no server should not need one to ship its own releases. Until this week, ours quietly did: cutting a release tag made one machine SSH into the others to build each platform — a private network, a set of credentials, and a hardcoded list of hosts that had to stay correct or the release broke. This week we removed every one of those SSH and SCP calls and replaced them with our own peer-to-peer work queue. A release tag now enqueues a declarative build pipeline; runners lease each stage by capability and move the artifacts between themselves over the same content-addressed transport the rest of the system already uses. We also say plainly what is proven and what is not yet, because the release path is exactly the wrong place to overclaim.

There is an embarrassing dependency that hides inside almost every self-hosted, "own your infrastructure" project, and we had it too: the release pipeline. The whole pitch of this system is that it is whole in itself — no cloud you have to trust, no server that has to be up, no account that can be closed. And then, quietly, the machinery that built and shipped the releases did the one thing the product refuses to do. It reached out over SSH.

The wrong dependency, named plainly

Here is what actually happened when a v* release tag landed, before this week. A handler in our CI engine walked a list of hosts and, for each one, ran the moral equivalent of:

ssh <host> "cd repo && naoms dist <platform> --json"
scp <host>:<artifact> .
ssh <host> "ln -sf <artifact> latest"

Read that and count the assumptions. It assumes a specific host — named, resolved, reachable right now. It assumes a credential — an SSH key that works, on an account that still exists, that hasn't rotated. It assumes a hardcoded map from platform to machine that a human has to keep correct: if the Linux builder moves, or a key changes, or a host goes dark, the release doesn't degrade — it breaks, at the worst possible moment, on the one workflow you run least often and trust most.

And it assumes a network that is not the product's network. SSH is a fine tool. But it is somebody else's plane of connectivity, layered underneath the peer-to-peer mesh the system already runs on. We were carrying two networks: the real one, that the whole design is built to make unnecessary, and a shadow one made of SSH config and host aliases, used only to ship the thing whose entire point is that you don't need a shadow network.

That is not a performance problem. It is a wholeness problem — the axiom that says a thing should be complete in itself, with no external dependency for its core function. Shipping your own releases is core function. Ours leaned on scaffolding the product was designed to eliminate.

What replaced it

The rewrite removed every SSH and SCP call from the release fan-out handler — runNaomsOnHost, the remote command builder, the SCP upload, the ssh ln -sf that repointed "latest", and the whole hardcoded host-alias map that fed them. Verified structurally, not by hope: the branch has zero ssh/scp call sites, both in the raw source and with comments stripped, and a test spins up a global spy on process spawns that fails loudly if a single ssh or scp ever runs.

In its place, the handler does something much smaller and much more honest. It enqueues a declarative pipeline. A release tag now drops the release-multiplatform pipeline — the one already written down in our CI configuration — onto a work queue that lives on the mesh itself, as ordinary signed events on a queue chain that syncs peer-to-peer. This is not a new bespoke path invented for releases; it is the exact same route a normal push-triggered build already travels. Release-building stopped being a special, privileged, SSH-shaped act and became just another job on the same queue as everything else.

From there the work finds the machines instead of the machines being named:

flowchart TD
    A["release tag v*"] --> B["handler enqueues the
release-multiplatform pipeline
onto the mesh work-queue"]
    B --> C{"picker leases each stage
by capability_required tag"}
    C -->|"builds: linux"| D["a runner that can build Linux
runs the real desktop verb
→ .deb / .AppImage"]
    C -->|"builds: android / mac / …"| E["a runner with that capability
runs that stage"]
    D --> F["artifacts flow to downstream
stages over content-addressed
peer-to-peer transport"]
    E --> F

Two things are worth slowing down on. First, selection is by capability, not by hostname. No stage says "go to that box." A stage says "I need something that can build Linux," and the picker leases it to whatever runner advertises that capability tag. Machines can come and go; the release doesn't care which one answers, only that one that can does. Second, the artifacts move between runners over the same content-addressed pipe the rest of the system uses to move files — the bytes are named by their content and pulled point-to-point between the two peers that need them, not shuttled through a copy command against a named host. (Why bulk bytes ride a direct content-addressed channel and never the gossip layer is its own story; the release pipeline is now a first-class citizen of that same discipline.)

There is also a small, deliberate sharp edge: there is no SSH fallback. If the queue isn't there, the handler does not quietly find another way — it refuses, loudly, and retries on the next tick. A fallback to SSH would have re-introduced the exact dependency we were removing, and a silent one would have hidden that it happened. An honest loud failure that resolves itself next cycle is the correct shape. It also happens to be the only shape consistent with not carrying the shadow network anymore.

What is proven, and what is not

Now the part that matters most, because a release pipeline is precisely where you must not round up.

What is proven: the handler no longer contains a single SSH or SCP call, and that is checked by a controlled test that would fail if one crept back in — the test was watched to go red when SSH was deliberately re-injected, then green when it was removed, so the check has teeth. The underlying mechanism it now depends on — enqueue a pipeline, land it as job_enqueued on the mesh-synced queue chain — is itself proven end-to-end by a separate integration test that drives the identical enqueue path a normal push uses.

What is not yet proven, stated in the merge commit itself and carried into main unweakened: the release-tag path's own full run, end-to-end, against a real live queue producing real signed artifacts across real machines, has not yet been demonstrated. The pieces are each proven; the whole release, driven from a real tag through to shipped bundles over the mesh, is a run we still owe. Landing this was a correctness fix — main was violating a stated requirement by shipping over SSH at all — not a declaration that the new pipeline has cut a release in anger.

We could have written this article as "releases now go peer-to-peer, done." It would have read better. It would also have been the completion illusion — the failure mode where "the code is right" gets quietly promoted to "the thing works." The code is right: the wrong dependency is gone, verifiably. The last mile — watching a real release fan out over the mesh from tag to bundle — is a task on the board, not a claim in the past tense. When it's green, you'll read about that too.

The cord is cut. The shadow network is gone from the source. What's left is to run the release we can now, at last, run without it.
