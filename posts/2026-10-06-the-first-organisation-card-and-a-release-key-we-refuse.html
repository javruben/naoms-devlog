The first organisation card, and a release key we now refuse

A hive can now sign a card about itself (groundwork only, nothing in the app shows it yet). A release build now refuses a signing key that is published in the repository. And a handful of quieter fixes replaced waiting or silence with a named answer.

Technology Teacher free October 6, 2026·6 min read·craft
TL;DR This post covers what landed on main after the install-card post of 2026-10-05, up to the commit named in the body. Three things are the point. An organisation card is a signed credential a hive issues about itself; the builder, signer-side format and verifier exist, and nothing in the app creates or shows one yet. A release build now refuses a signing key that is published in the repository as a test key. The Hermes daemon bundle builds again after a dependency-resolution fix. Smaller entries cover a file request that no longer waits out a timeout, a `naoms publish` command that approves only its own request, and a rule that a local model's tool call runs only as the last thing it writes.

This post covers what reached main after the install-card post of 2026-10-05, up to commit 910a221a3a2 at the time of writing (2026-10-06, early morning UTC). The site-viewer feature that landed over the same days has its own post, "A zip file becomes a website you can open inside NAOMS". Later work will be in a later post.

Some words first

A hive is a group of people sharing a record. A verifiable credential (VC) is a small signed statement: who says it, what it is about, and a signature anyone can check against the issuer's public key. A release key is the key whose signature tells an installed NAOMS that a build is the real one. A daemon is the background program on your device that holds your data. Hermes is a small JavaScript engine. NAOMS builds a daemon bundle for it, which the commit messages call the Hermes daemon bundle; the header of the bundler's own test describes it as the mobile Hermes daemon bundle, dist/daemon-bundle.js, which is embedded into the mobile core library (libnaoms_core.so) at build time (src/packages/clients-bundler/tests/uc-hermes-daemon-bundle-compiles-success.test.ts).

The first organisation card

An organisation card is a VC that a hive issues about itself. The issuer and the subject are the same hive, and the signature is made with the hive's own contract-branch key (89843c4a62a). The code's header comment is blunt about what it is not: a hive is not a legal organisation, and the card asserts what the hive says about itself and nothing about legal status.

What landed:

  • A builder that produces the card body, a verifier that checks the signature and shape, and a function that finds the hive key to verify against. The card has a required set of fields in one place: hive id, name and country. The builder and the verifier both read that one list, so adding a required field later is one edit. Refusals have named codes, for example a missing required field, an issuer that does not match the hive, or a bad proof.
  • A declaration, hive.org_card.published, registered for the hive's contract chain, and the card kind classed as something peers may read and as trust-bearing, because an existing static check fails when a shared kind is left unclassified.

What did not land: the code that signs a card is a later step (the header says the caller supplies the signer), and nothing in the app creates, shows or publishes a card. This is groundwork. We looked at the production source files that mention the card (five, outside tests: the card module itself and four registry or routing files) and none of them is a screen.

A release key we now refuse

The repository publishes test signing keys, on purpose, so tests can sign things without a real secret. A release signed with one of those keys would carry a signature anyone could forge. b0fe7bac473 adds a short fixed list of the published test public keys to the release tool, and dist now refuses a build whose embedded release key is on that list, with the named error release-key-is-published-test-key. The named refusal wins over the generic "key does not match" message, and it fires even when the key in the build equals the signing key (that is exactly the case it exists for). A drift test checks that the list equals the keys derived from the published test seeds.

The follow-up, 00443644ce6, moves the signing-key half of that check to the very top of the build, before submodules, compiling or any remote copy, and makes it apply to every build strategy, including the one that builds on another machine over ssh. The tests drive the real build function against a fake ssh that records every call, and check the fake is never called when the key is a published one.

The commit messages name what this does not cover: this particular check does not refuse a build that has no signing key at all (an unsigned build), because with no signing key given the check skips reading the embedded key. How unsigned builds are handled elsewhere is outside this post, and we make no claim either way about whether one can ship. On the ssh strategy the embedded-key readback is moot because that path still bakes in an all-zero placeholder.

The Hermes daemon bundle builds again

380cfbc231f says no Hermes daemon bundle could be built from main since 2026-10-05, because one import was written as npm:ajv@^8.17.1/dist/2020.js and the bundler's resolver only knew how to strip a version when it ended the name. Now it strips the version range before a subpath, and ajv, the library behind the trust-task payload-schema check, is bundled for real rather than stubbed, because a stub would turn that check off. cbaae56d67d goes further: a bundled package resolves only from the exact version pinned in the lockfile, and a range the lockfile does not pin, or an installed version that differs from the pinned one, fails the build by name. Any other package that is not on the bundle allow-list still fails loudly. The merge on main is a216ae066b2.

Quieter fixes that replaced silence or waiting

  • A file request that cannot be sent no longer waits. eeabdc047a5: a rejected send (for example one a device refuses to address to itself) used to escape as an unhandled error while the caller waited out an 8-second timeout. It now resolves with "no result" at once.
  • naoms publish is a command of its own, and approves only its own request. a5d838d202d adds the bare naoms publish and a --auto-approve flag; a refused publish now lists each violation as rule, file and line. 1e9d32da325 and 7ddaf494803 make --auto-approve grant only the approval request the command itself caused: an approval for a different operation or a different payload is not granted, and the command stops with a named error. The commit messages list the commands not yet moved over (repo add, cache and onboarding).
  • A local model's tool call runs only if it is the last thing it wrote. a20d53154b4: a tool call written as text in the middle of a reply, or quoted in prose, is not run. The stream shows "[tool call not run: model wrote it mid-reply]", a warning is logged, and the original text is kept. 9f9e0d72286 made the same detector tolerate a model that wraps its JSON in a code fence.
  • "This device" means this device. 7fe85c4b910: the function that names this device's key used to return the newest device row, which names a different device once two devices have synced. It now anchors on the daemon's own key, and logs once when it cannot answer yet instead of returning nothing silently.
  • Flow placement reads live liveness. 31f68020a74: choosing where a flow runs now reads the newest weather heartbeat of this device and its siblings on the chain, and falls back to the declared state for a device with none.
  • Batch writes honour package guards. 5cb9766f14c: the batch append path now runs registered package event guards once per event before anything is stored; one rejection rejects the batch.
  • A governance override flag is test-only. 72fc63f9938: the flag that lets a repository accept self-attested governance counts only in test mode, and is refused by name, with an error, anywhere else.

What we did not verify

  • We read commit messages and diffs. We ran nothing for this post, and the test results quoted are those the commit messages record.
  • We did not exercise the organisation card on a running daemon, and we know of no screen that uses it.
  • We did not build a release or run dist to see the key refusal fire. The point that this check does not cover an unsigned build is from the commit message, and we did not look at how unsigned builds are handled elsewhere.
  • We did not build the Hermes bundle, or run anything on a phone. The statement that the bundle is embedded in the mobile core library is from the test header, not from our own check of the build.
  • Several entries, such as the flow-placement and "this device" fixes, record that their tests were written against a single venue's code and libraries; we did not re-run them elsewhere.
  • This post is a selection. Main also took test-only, checker and roadmap changes in this range that we did not describe.
