A store that checks where a picture came from

Five changes from one day: store pictures tied to the publisher's own release, installs that ask for a second signature on channel-announced packs, a group of templates adopted behind one consent screen, an agent time limit that now says when it clipped your request, and video calls that turn away removed members.

Technology Teacher free October 2, 2026·6 min read·craft
TL;DR This post covers what landed on main on 2026-10-02 (UTC). The in-app package store changed how it gets a listing's pictures: through one operation that serves a picture when it came with that package's release from its publisher, and a placeholder otherwise. Installing a pack announced on a channel now asks for a countersignature from someone other than its publisher, judged per release. A pathway of several templates can be adopted in one batch behind a consent screen that names each member. An agent run whose requested time limit was clipped now says so, and a run waiting for a human answer is no longer treated as stalled. Video-call admission now refuses removed members and revoked devices, and revocation removes them from live rooms. Several of these are first versions with stated limits, listed at the end.

This post covers 2026-10-02 (UTC), meaning commits that landed on the main branch between 00:00 and 24:00 UTC that day. There were many more commits than appear here; I picked the changes a reader outside the project can learn something from.

Some background first. NAOMS stores state in chains: append-only logs of signed entries, where each entry says who wrote it. A package is an installable unit of software or policy, and a channel is a shared chain where members announce packages to each other. A daemon is the background process on your device that does the work and that the apps talk to. With that, here is the day.

1. Store pictures that must come from the publisher

A store listing has a banner and screenshots. These are stored as content-addressed blobs, meaning a picture is named by the hash of its bytes, so a name always identifies exactly one set of bytes.

The question the store has to answer is: when a listing names a hash, where may the picture come from? Before this change the store page itself fetched blobs by hash. That has two problems the commit message names. First, a page that will fetch any hash can be tricked into showing something that lives only on the viewer's own device. Second, "found" versus "not found" tells an outsider whether a hash exists locally.

9496e0a3073 replaces that with one daemon operation, marketplace.listing_image. It takes a package id and a hash and works like this, per the commit:

  • the package's latest release must itself name that hash;
  • the publisher's identity and node are read off that release;
  • the picture is served only if the device already holds a provenance record for that exact package, version, publisher and hash; otherwise it is fetched from the publisher's node alone, checked against its BLAKE3 hash, and a provenance record is written;
  • it enforces a 4 MiB size cap and a list of allowed image formats, checked by the first bytes of the file rather than the file name;
  • every failure returns the same answer, "unavailable", so the answer leaks nothing about what exists.

The store page no longer reads blobs itself, and its file-read permission for blobs was removed from the manifest. When a picture is not available, 7814c1e29f4 shows a neutral "Image not available yet" placeholder inside the image's own box, rather than a broken image or a substitute picture.

2. A second signature on channel-announced packs

A countersignature is a second signature, from someone other than the publisher, vouching for the same release. Installing a package that a hive (a group of people sharing a chain) announced already required one from a member of that hive.

The gap: packs announced on a channel were skipped, because the check returned "nothing to verify" for any pack without a hive target. 4f8aea55042 closes it. A pack whose announcing chain is a channel, and which is not the repository itself, is now checked against that channel and refused with a named error if no non-publisher countersignature exists. The pack's own publisher does not count as the second signer.

A follow-up, 17fc427e5f4, fixed where the check looks. The store keeps one summary card per package, overwritten by each new announcement, so a later announcement elsewhere could change the card and lift the requirement. The check now scans the announcement rows for the exact release (package, version and content hash) across every chain on the device. Each announcement adds a requirement and all must hold; a release with no announcement row on the device is refused as unverifiable. The commit discloses a test-fixture change: some "repo-only" controls had not actually been repo-only, and a new option makes them so.

3. Adopting a group with one consent

A pathway is a package that declares several member templates, for example procedures and policies for onboarding. Adopting it means writing the adoption onto your own chain.

ba875c924a2 makes the group adoptable as a unit, reusing existing event shapes rather than inventing a new one. All member adoptions go into one batch, and every member is validated before anything is written, so the first bad member refuses the whole group. The commit is explicit that this makes the append atomic, not the later projection (the step that turns chain entries into what the app shows), whose failures are recorded, not rolled back. Provenance on each member is marked "claimed": signer and signature are recorded, not verified.

4125edc5295 adds the button. It opens a consent panel naming every member, because adopting writes one entry per member and a dialog that only says "adopt this pathway?" understates that. The success line is built from what the handler reports it wrote, not from the listing the page already showed.

4. An agent time limit that admits when it clips you

An agent run here is a long-lived AI task with a configured maximum duration. 96106b3a3dd fixes a silent clamp: a caller asking for 7,200,000 ms had the run die at 1,800 s with no log and nothing in the result. The cap is unchanged, but now a warning names requested and effective milliseconds and the config key, and the result carries timeoutClamped with those values.

26587338bd2 fixes a related misjudgement. An agent can run in a progress-bounded mode, where it is aborted as stalled if it makes no progress. One such run was aborted about 20 minutes after it asked a human a question and was waiting for the answer. The tracker can now pause its stall clock while a human-wait tool is in flight; the overall ceiling is not paused.

5. Video calls that turn away removed members

Group calls on NAOMS run through a relay that forwards media between participants. b392cb50cb8 adds one admission check, used when joining, when the relay admits someone, and in the call message handlers. It refuses a member who has been removed, and a device whose key was revoked. A second commit, 74e05ace4bf, makes the relay's admission predicate a required argument (missing means deny), makes a refused join roll back, and evicts a revoked participant from rooms that are already live, including removing their leaf from the group's encryption state.

A small one: reporting a bug from a listing

790858b67fb makes the Report a bug control validate the package name and version when reading a report back, flagging malformed values rather than showing them, and shows a sentence beside the control saying the report, including the package name and version, is visible to the project maintainers' channel.

What we did not verify

  • Test results are quoted as the commit messages record them; I did not re-run anything.
  • The pictures change records its own checks on one machine; I did not check it on a phone or a fresh install.
  • Provenance on adopted members is "claimed", not verified, as stated in section 3, and the group adoption targets your personal chain only. Adopting into a shared hive is described by the commit as a later, larger piece.
  • The countersignature check refuses releases it cannot find an announcement for; whether that is too strict in everyday use is not measured.
  • I have not measured how the call-admission change behaves in a real multi-device call; the commits record unit-style tests only.
  • Other commits that day, in areas I did not read closely, are not covered.
