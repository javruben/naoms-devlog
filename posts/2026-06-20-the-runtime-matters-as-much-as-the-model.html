Where You Run a Local Model Matters as Much as Which Model

We measured the same model file at 96% reliable on one runtime and 20% on another at actually doing what it's asked — then made the first action land reliably across all of them.

Technology Architect free June 20, 2026·3 min read·local-ai
TL;DR If you run a local model to power an assistant, how reliably it actually does what you ask — instead of just describing it — can swing wildly with the runtime you run it on: we measured the same model file at 96% on one and 20% on another. We're rolling out a fix that makes the first action land reliably across all of them; it's at 100% in our tests.

When you run an AI model on your own machine to power an assistant, you pick the model — some flavour of qwen, llama, whatever you trust. What almost nobody tells you is that you also pick the runtime: the separate program that actually loads the model file and runs it. Ollama is one. llama.cpp is another. There are several. We used to file that under "plumbing detail." Then we measured it, and it turned out to matter enormously.

The measurement that surprised us

We took one specific thing an assistant has to get right — when you ask it to do something, it should actually take the action, not just write a paragraph describing what it would do — and measured how often a model got it right across different runtimes. Same model file. Same prompt. The only thing that changed was the program running it.

The spread was startling. The identical model file took the action 96% of the time on one runtime and 20% of the time on another — a 76-point cliff. A third sat around 40%. Which runtime you happened to pick mattered as much as, sometimes more than, which model you picked. That is not how anyone talks about running local models, and it should be.

Why this is dangerous for a local-first assistant

This is exactly the kind of thing that can quietly wreck the promise. The whole point is that your AI runs on your own machine, answering to you, on whatever model you choose to trust. But if whether it actually does the thing secretly depends on an invisible runtime choice, then "run your own model" comes with a hidden reliability lottery — and the person holding the ticket is a user who never knew they were playing.

The fix, and what it actually closes

So we closed it, at least for the most important moment: the first action. The fix is almost embarrassingly small once you see the failure. On that first turn, when the assistant should do exactly one thing, we hand the model a list with exactly one tool on it — nothing to get distracted by, nothing to talk itself out of. With that, first-action reliability went to 100% on every one of the five runtimes we tested — across 329 trials. The runtime stops being a lottery for that first, decisive step.

This sits underneath the same idea as giving you one door for every model you run and letting you reach for the big model or the local one as the job demands: the machinery should make your choice of model and runtime work, not quietly punish it.

What's real, and what's still rolling out

The discipline here is to never dress a draft up as finished. So: the finding is solid and measured, and the first-action fix is real and proven at 100% across five runtimes. What's not done yet — the full multi-step case is closed on two of those five runtimes, with the rest being measured now; and the fix is something we can switch on, not yet the default for everyone while we finish extending it. The hard part — knowing the runtime is a first-class variable, and having a mechanism that flattens it — is in hand. Turning it on everywhere, by default, is the work in front of us.

The lesson we're keeping is bigger than the patch: when you run models locally, the runtime underneath them isn't a detail. It's a variable in whether the thing works at all — and we're measuring across runtimes now, not just across models, so that "it did what you asked" stops depending on a choice you didn't know you were making.
