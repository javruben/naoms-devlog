The Day a Frozen Object Broke Every Dynamic Feature

How one 'obviously harmless' hardening line quietly took down every tab in the app

Process Confession free April 10, 2026·4 min read·clients
TL;DR A confession: the change we were surest was safe — locking down a list so nothing could tamper with it — quietly knocked out consent, vault, contacts, hives, and every other tab. Here's how the safe-looking bug is the dangerous one.

The most dangerous change you can ship is the one that looks safe.

Not the gnarly refactor — you're careful with those. Not the thing you half understand — you test that twice. The dangerous one is the tidy little hardening that any reviewer would wave through, because it is obviously correct and obviously harmless, and so nobody looks hard enough to notice it is neither.

On 2026-04-10 we shipped one of those.

The "harmless" line

The feature registry in the NAOMS browser client is a plain object that the app hangs onto in the page. Dynamic feature modules register themselves into it as they load: consent, vault, contacts, hives, and a couple dozen others. It is the table that says "here are the tabs this client knows how to render."

As part of a hardening sweep we did the thing that every security instinct applauds: we froze it. Object.freeze on the registry. The reasoning was airtight and we can still feel how reasonable it sounded — nothing should be able to tamper with the feature registry after it's set up, so freeze it and make tampering impossible. One line. A lock on the door. Ship it.

What actually happened

The registry was frozen before the dynamic feature modules could register themselves into it.

Freezing an object in JavaScript doesn't just prevent overwriting existing keys — it prevents adding new ones, silently, in non-strict code. So every feature module that loaded after the freeze tried to register, found the door locked, and failed without a sound. No exception bubbled to anywhere we were looking. The tabs just... weren't there.

The revert records the body count plainly: the object was frozen before the dynamic feature modules could register, and the result was that consent, vault, contacts, hives, and all other package UI tabs silently failed to load. Not one feature. Not a category of features. All of them. The only things that worked were the six features preloaded before the freeze ran — out of more than thirty.

How it was caught

This is the part we want to be honest about, because it is the part that should have happened before the freeze shipped, not after.

The diagnosis came from opening the browser dev tools and asking the object directly. Was it frozen? Yes. The registry had six entries where it should have had thirty-plus. There was no stack trace pointing at the freeze, no error in the console screaming "you can't add a key to a frozen object" — because in the non-strict path the addition just no-ops and returns. The failure was silent, which is the worst adjective a failure can wear. A loud failure is a free bug report. A silent one is a treasure hunt where the treasure is your own mistake — the same lie we went hunting for in the errors we were swallowing.

We had to go look at the live object in a running browser to see that the lock we'd installed for safety had locked out the entire feature set.

The fix, and the thing we'd actually wanted

The fix took one line off and put a better one on. Remove the freeze. Keep the per-key guard that prevents overwriting an existing feature — which, it turns out, was the real security need all along.

That is the whole lesson. We never actually needed to prevent additions to the registry — adding features is the registry's entire job. We needed to prevent overwrites, so that a malicious or buggy module couldn't replace the consent feature with something pretending to be it. Those are different threats, and a blanket freeze is the wrong tool because it answers a question we weren't asking. It locks both the additions we needed and the overwrites we feared, and the collateral damage was every dynamic tab in the product.

The confession

The bug is not that we reached for a hardening primitive. The bug is that we reached for the broadest one available and never asked what it actually restricted. "Freeze it" felt like the maximally-safe choice precisely because it is maximal — and maximal restriction, applied to a thing whose job is to grow, is just breakage wearing a security badge.

We think about this one whenever we're about to add a lock. The honest question is never "is this more locked-down?" It is "what specifically are we trying to prevent, and what is the narrowest mechanism that prevents exactly that and nothing else?" A per-key overwrite guard was that narrow mechanism, sitting right there the whole time. The blanket freeze was the lazy maximum, and the lazy maximum took down consent, vault, contacts, and hives for the cost of feeling responsible.

Safe-looking is not safe. The tidy one-liner is the one to read twice.
