Four things changed this week

One per major area. Almost none of it is visible on screen — this is the week the plumbing got serious and the pixels took a break.

1

Every change to your data goes through one signed path

The old direct-write shortcut is gone. Every write is signed, audited and projected the same way, so nothing can quietly write around the record.

2

Our own checker can fix many of the problems it finds

A three-tier engine handles mechanical edits itself, uses a local model for the trickier rules, and checks each file afterwards so a bad machine edit cannot poison the run.

3

Setting up an account drives the real onboarding

The development and test path now runs the genuine onboarding flow rather than a shortcut around it, so the thing being tested is the thing people get.

4

Eleven re-encryption gaps were closed

Five critical and six high-severity gaps, found by an earlier review that discovered protections marked done which were in fact dead code, disabled, or silently violated.

One door in

The feature: every change to your stored data — every memory, every grant, every setting — travelling through a single path that signs it, records it, and updates the queryable view from that record.

Stored data here means everything the system holds on your behalf: the memories themselves, the grants that say who may read them, the settings that shape how it behaves. All of it moves through the same door now.

Before: code could write two ways. A raw direct write here, an audited append there. Now: there is one door, and the raw one has been bricked shut across the whole codebase.

Two write paths is not an unusual state for software to be in. It is the ordinary result of a system growing: the careful path is built for the cases that need it, the quick path survives from before, and both are correct in isolation.

A system with two write paths does not have an audit trail; it has an audit sample. Half the writes skip the signing, the audit record and the projection step. What is left is state whose provenance nobody can establish, which is the same as state you cannot trust.

What was built. The direct-write shortcut was funnelled into the single audited path everywhere it appeared. That change broke 130 import sites at once, which is the honest measure of how widely the second door had been used.

A shortcut is also cheaper at the moment it is used, which is why it spreads. Each individual bypass is a small, defensible saving; the aggregate is a system that cannot account for its own state.

Breaking 130 things in one afternoon is the kind of pain you pay once so that you never again have two ways to write. Spread over months it would have been cheaper per day and never finished, because a migration with both roads open has no forcing function.

The 130 number is also a measurement of something nobody would have gathered otherwise. Nobody sets out to count how many places bypass the audited path; you find out by closing it.

Why the projection has to come from the log

A chain is an append-only record of signed events. The graph everyone queries is a projection of that record — a view built by replaying it.

Replaying is the useful property. A projection can be rebuilt from scratch at any time, which means a bug in the view is a bug you can fix and re-derive rather than a corruption you have to repair in place.

That arrangement only holds if the record is complete. One unaudited write and the graph contains something the log cannot account for, and from then on the two disagree in a way nothing detects.

Funnelling every write through one path means the queryable view is always a faithful projection of an accountable log. It is not a performance property or a tidiness property. It is the difference between a system that can explain itself and one that cannot.

One door also makes a whole class of question answerable. Who changed this, and when, and under what grant, stops being an investigation and becomes a lookup.

The cost is real: one path is a bottleneck by design, and every future feature that wants to write has to go through it. That constraint is the feature.

What this does not yet do is prevent a second door being cut. The migration removed every shortcut that existed; nothing described here refuses a new one, and a rule that has to be remembered is a rule that will eventually be forgotten.

One door in is the longer account.

A checker that fixes what it finds

The feature: the automated checker that reads our code for rule violations can now repair many of them itself rather than only reporting them.

Before: the checker produced a list and a person worked through it. Now: it produces a list and fixes the parts it can, in three tiers of increasing caution.

Rule checkers accumulate findings faster than people clear them. A list of several thousand violations is not a to-do list; it is a backlog that everyone learns to scroll past, and the checker stops changing anything.

A machine that edits code is only as useful as the check that follows it. Automatic repair is easy to build and easy to regret, because a confidently wrong edit applied at scale is worse than the violation it replaced.

Onboarding changed for a related reason. The development and test path used to take a shortcut around the real setup flow, which meant the thing being exercised every day was not the thing a person receives. It now runs the genuine flow, and the standalone governance command was removed so that governance folds into the policy engine rather than sitting beside it as a second way in.

What was built. Three tiers. Mechanical edits, where the fix is deterministic and there is nothing to decide. A local model for the rules that need judgement. And a per-file safety check after the fact, so a bad machine edit cannot poison the run it was part of.

The middle tier is the one worth noticing for its constraint rather than its capability: the model doing the judging runs locally, on the same principle that has governed every model decision since the first week.

Splitting repair into tiers is what makes automatic editing defensible at all. The mechanical tier needs no trust because it has no judgement. The model tier has judgement and therefore needs the tier that follows it.

Why the third tier is the one that matters

Trust in an automatic editor is not a single decision. It is granted per tier, and the tiers exist so that the grant can be different for each.

Tiers one and two produce edits. Tier three is what makes the edits safe to accept, by verifying each file on its own after the change rather than verifying the run as a whole.

A local model is doing the judging, which means the checker's harder tier works without an outside service and without sending the code anywhere. The same constraint that governs the product governs the tooling that maintains it.

Per-file is the important word. A run-level check tells you something went wrong somewhere; a per-file check tells you which edit to reject and lets the rest stand. One is a rollback, the other is a filter.

This is also where the week's other numbers come from. The campaign to drive rule violations to zero is the slow, rule-by-rule work; the autofixer is the lever that makes it tractable. Neither is finished.

The open question is what happens to a wrong edit that looks right. Every mistake caught so far has been one the per-file check could see; a plausible, well-formed, incorrect change is a different problem and has not been tested against.

Teaching a checker to fix its own findings covers all three tiers.

What this means, in plain terms

Most of what lands in a week belongs to the thing it landed in. A few things generalise past it. These five are the ones this week actually paid for — each learned by getting it wrong somewhere first.

Two ways to write the same state is one way plus an unaudited one

Funnelling every write through a single signed path broke 130 import sites, which is how much the second path was being used. A system with a shortcut has no audit trail, only an audit sample. The migration is finished when the old road is impassable, not when the new one exists.

Hardening applied at the wrong moment is an outage

Freezing the feature registry was a safe-sounding change that ran before the dynamic modules could register into it. Consent, vault, contacts, hives and every other tab silently failed to load; six of more than thirty features survived. A protection has a correct time as well as a correct shape.

Text from a failure is still untrusted input

The client was rendering raw error text as live markup, so a message coming back from a failed request could carry an injection. The fix builds the elements explicitly and renders the text as text. Nothing becomes safe by arriving on an error path.

A control nobody exercised is a claim, not a control

An earlier review found re-encryption protections marked as done that were dead code, disabled, or silently violated in practice — eleven gaps, five of them critical. The status was accurate about intent and wrong about reality. Verify a security control by making it refuse something, not by reading that it exists.

Give an automatic editor something that can overrule it

The autofix engine makes mechanical edits, uses a local model for harder rules, and then checks each file so a bad edit cannot poison the run. Without the third stage the first two would be an efficient way to spread a mistake. Any process that writes at scale needs a reviewer that is not itself.

What would prove this week's audit claims wrong

Five things this report claims are only half-proven, and the week's own history is the argument for reading them carefully: an earlier review found protections recorded as finished that were not.

Each is stated as a commitment, and each names the evidence that would settle it, so that a later window can check this one rather than take its word.

  • One write path is enforced by a migration, not yet by a gate. The shortcut was removed everywhere it appeared. Nothing here stops a future change from adding a second door, and only a check that refuses one would.
  • The autofixer's safety check has not met a determined bad edit. Per-file verification catches the mistakes seen so far. Whether it catches a plausible, well-formed, wrong edit is untested.
  • Eleven closed re-encryption gaps came from one review. The gaps found were fixed. A review that found protections marked done which were dead code is also evidence that the status field cannot be trusted elsewhere.
  • 227 strict-type errors are still open. They are counted and listed and none of them is fixed. The count is honest and the state is not good.
  • The frozen-registry outage has no guard behind it. The change was reverted the same day. Nothing described here prevents another initialisation-order change from doing the same thing next month.
