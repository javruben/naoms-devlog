Refusing To Overwrite What You Cannot Open

The keys that prove you are you have no password reset, so the vault holding them enforces one rule: nothing may overwrite key material it cannot itself open. Where that rule lives — on the write, not on the callers — is what makes it hold.

Product Architect free August 25, 2026·5 min read·sovereignty

The keys that prove you are you are not stored anywhere you can retype them from. That's the whole idea. There is no password reset, because a password reset is just someone else holding the real key.

Which means the file holding those keys has an unusual property: it is simultaneously the most important thing on the disk and, to any program that happens to have write access, an ordinary file.

The invariant

The rule the vault enforces is one sentence:

Before writing key shares, the incoming key must be able to open whatever is already there.

If it can, this is the same identity re-saving its own material — proceed. If it can't, this key doesn't own what's there, and writing would destroy someone else's keys. Refuse, loudly, with an error that says why.

The comment sitting next to it in the source puts the stake plainly: overwriting "would silently destroy another identity's FROST material."

What makes this worth writing about is where the rule lives. It is not a check performed by the callers who might do the damage. It is a condition on the write itself, so it holds no matter who is calling, from what process, with what configuration — including callers that don't exist yet.

Here is the failure that made the case for putting it there:

A test harness isolated its database and its keys directory into a sandbox, but not one other environment variable. The signer derived its key-shares path from that variable, found it unset, and fell back to the real one in the real home directory — writing throwaway test keys into the vault holding the real ones. Every subsequent boot failed to decrypt. The daemon didn't crash; it logged that unlock had "succeeded," dropped into a mode where it could not sign, and reported not-ready in a health field. Recovery meant wiping the vault.

Why the guard sits at the write

There is an obvious alternative: fix the callers. Set the missing variable in that harness, then audit every other one for the same omission.

That was done for the harness in question, and it was explicitly not treated as the protection — because callers are a set that grows without your permission. Every new test file, every script someone writes next year, every tool that spawns a daemon is another chance to omit the same line. Guarding the callers is a promise that nobody will ever again make a mistake that has already been made.

Guarding the write is a different kind of claim. It doesn't care how a process got the path, which variable was unset, or whether the author had ever heard of any of this. A hundred future callers can all get it wrong and none of them can destroy the keys.

The general form, and it applies well beyond vaults: when an operation is irreversible, put the guard at the operation, not at the callers.

Why the guard is keyed on the recovery key

There is a design choice inside that invariant worth pulling out, because it is the kind that decides whether a guarantee actually holds.

An adversarial review proposed binding the owner's identity into the encryption itself, so a file sealed by a foreign identity would fail loudly on open.

It's a good instinct and it sounds airtight. Someone went to implement it and checked the load path first.

The crash-recovery path — the one that runs when the machine died unexpectedly and the daemon is coming back up — does not reliably carry the owner's identity. Those fields are optional, and have been for back-compat reasons since long before this bug. Recovery frequently arrives with nothing but the recovery key.

So binding the encryption to the owner's identity would have meant that crash-recovery could no longer reconstruct what it needed to decrypt. The fix would have bricked the vault on exactly the path the bug lived on — turning an occasional cross-process accident into a guaranteed failure after every unclean shutdown.

The resolution is the quiet lesson here. The property the reviewer wanted — a foreign seal must fail — was delivered by keying the guard on the recovery key instead, because the recovery key is reliably present at every save and every load. Same guarantee. Different anchor. The anchor was chosen for being always there rather than for being conceptually the right thing to name.

That's a real engineering trade and it goes against instinct. The owner's identity is the semantically correct thing to bind to; it is also the thing that is sometimes absent. A correctness property anchored to something occasionally missing is not a correctness property, it's an outage with good intentions.

The identity binding wasn't discarded — it stayed as a fixed constant for domain separation, which costs nothing and buys a little. It just isn't what's holding the roof up.

Two details that show the care

Old files still open. Every reader tries the new sealed format first, then the legacy one, and the next save quietly re-seals in the new format. Nobody's vault needed a migration; upgrading happens on the next write, invisibly.

And the reproducer test is a genuine reproducer: it fails against the code as it was before the fix. That sounds obvious and frequently isn't — plenty of regression tests are written after the fact against the fixed code and would have passed happily on the broken version, proving nothing. This one was demonstrated red first.

Why a personal system needs this more, not less

It is tempting to file all of this under "developer concern" — the scenario that exercised it involved a test process on the same machine as a real daemon.

But that framing belongs to software living in someone else's data centre, where your keys and the developers' machines are different worlds. Here the premise is that you run it, on your machine, with your keys. The processes sharing a disk with your vault are your processes: tools you installed, scripts you wrote, things you are experimenting with tonight.

So the population that can reach your key material is not a small set of insiders — it is everything you run. A guarantee that depends on all of them behaving is not a guarantee. One that lives on the write is.

And the shape generalises past test harnesses. Any process that inherits a default path inherits reach it was never meant to have. The sandbox that isolates three things out of four isn't a sandbox; it's a sandbox with a door in it, and the door is invisible precisely because everything works fine until the one time it doesn't.

The durable answer wasn't to find every door. It was to make the vault refuse to be written by someone who can't already read it.
