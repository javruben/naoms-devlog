Your Second Device Shouldn't Quietly Fail to Read Your Shared Stuff

The pubkey race in multi-device identity — and the wall our RED-first tests found behind it

Technology Architect paid · premium preview May 30, 2026·4 min read·identity
TL;DR When you add a second device, content sealed for your identity has to be re-sealed so the new device can open it — and a timing gap could let that silently fail. We've shipped the resend protocol that closes the race (2026-05-30); end-to-end two-device sync is still landing, blocked one layer up on cross-device replication.

This is a deep-dive about a single, sharp race in multi-device identity — and about the discipline that made us honest about how much of it we'd actually closed by the end of the week. The work is post-pair device sync; the production code for the resend protocol landed on 2026-05-30. The same day, our tests for it stayed deliberately red — and that's the more interesting half of the story.

The race

One person, two devices, one identity. When the second device is admitted to the identity's signer cohort, content sealed for that identity — shares, encrypted material — needs to be re-sealed so the new device can open it. The race is in the timing.

A sibling device can be admitted and start receiving sealed envelopes while its public key is, momentarily, stale on the sender's side. The code that applies a signer-admitted event hits a key fingerprint that doesn't match any local key. The question is: what does it do?

The wrong answer — and the original behavior — is to silently drop it. The code logged a warning that the fingerprint matched no local key, and moved on. From the user's seat, a device that should now be able to read shared content simply... can't, and nothing tells anyone why. A stale-key admission landed, the reseal never happened, and the gap is invisible.

The fix: ask for a resend, don't guess

The protocol that closes this is a resend request. Instead of dropping a fingerprint it can't match, the receiver explicitly asks for a resend; the sender reseals against the now-current key and re-emits; the receiver installs it. The design target is tight: a stale-key admission should turn into a successful install within two gossip cycles, end to end. That's the loop that landed on 05-30 — receiver-side and sender-side wiring.

sequenceDiagram
    participant S as Sender
    participant R as Receiver (new device)
    S->>R: sealed envelope (against stale key)
    Note over R: fingerprint matches no local key
    R-->>R: old behavior: silently drop + warn
    R->>S: new behavior: resend request
    S->>R: reseal against current key + re-emit
    Note over R: install — within two gossip cycles

Notice the shape: the system never silently admits a key it can't verify, and it never silently abandons a device that should be admitted. The no-match case becomes an explicit, observable request — not a swallowed warning. That's the Honesty axiom applied to a key-rotation edge: no silent drops.

The honest part: we shipped the protocol and the tests stayed red

Here's where we have to be precise, because it would be easy — and dishonest — to write "we shipped multi-device sync this week." We didn't. The resend protocol shipped on 05-30. The end-to-end behavior did not, and our tests said so loudly, on purpose.

This work was built RED-first: the integration tests were authored before the feature was green, written to fail until the real behavior works, and kept honest-red rather than quietly skipped. Two twins:

  • a success test — stale-key admission → resend request → reseal → install within two gossip cycles;
  • a failure-mode test — a non-matching-fingerprint envelope is not silently installed.

When we ran them on 2026-05-28, both were red — and not at the resend surface. They were red at a precondition, with a witness message that is worth reading verbatim from the test:

setup: cohort admission carrier never reached the sibling within 90 seconds

In plain terms: the tests couldn't even reach the resend path, because the thing that's supposed to announce "this sibling was admitted" to the other device — the cohort fan-out announcement — wasn't being emitted on chain creation at all. The resend protocol was the gap we meant to fix; the missing announcement was a deeper gap underneath it that the RED-first tests surfaced before we'd have found it by hand.

So the week-11 honest status of this work is a stack of three gaps, discovered in order:

  1. Resend protocol unbuilt — the resend request existed nowhere in the source on 05-28. Fixed 05-30.
  2. Cohort fan-out announcement unwired — the admission announcement wasn't emitted on chain-create, so no sibling ever heard about the admission. Wired shortly after.
  3. Cross-device commit replication — even with the announcement emitted, the admission commits weren't replicating to the sibling chain in time. This was the wall still standing when the dust settled, and it pushed the end-to-end green into early June.

We're telling you all three because the alternative — claiming the feature shipped because one of its three layers shipped — is exactly the kind of green-over-a-gap lie the project exists to refuse.

Why RED-first earned its keep here

If we'd written the tests after building the resend loop, they'd have gone green against a mocked-up announcement and we'd have shipped a feature that doesn't work end-to-end on two real devices. Writing them first, against real daemons, forced the precondition to be real — and the precondition is where the actual bug lived. The resend protocol was never the hard part. The hard part was a missing announcement two layers up, and only an honest, refuse-to-skip test could point at it before a user did.

That's the lesson worth paying for: the value of a RED-first test is not that it eventually goes green. It's that, while it's red, it tells you the truth about which layer is actually broken. On 05-30 it told us the resend loop was done and the replication wasn't — and we wrote that down instead of rounding up.

Where it stands

As of week 11: resend protocol — shipped (05-30). Cohort announcement — wired. End-to-end two-device install — not yet, blocked on cross-device commit replication, landing-ward into June. One honest sentence, three honest clauses.
