Your device should only sign what you wrote

One day of security fixes on the peer-to-peer layer had the same shape four times: a message arrived carrying a claim about who it was from, and the receiver believed the claim instead of checking the signature. Here is what each fix closed, how it was measured, and what is still only an interim answer.

Technology Teacher free September 29, 2026·7 min read·craft
TL;DR On 2026-09-29 (UTC) a run of fixes closed four places where NAOMS believed a message's own claim about its author: a device that re-signed any unsigned chain commit a peer sent it under its own key, an import path that stored commits without checking signatures, a handshake frame that let a stranger take over a connected friend's network identity, and governance votes that named their voter in the payload instead of proving it with the signature. Each fix came with a test that fails on the old code and passes on the new, and the handshake one was measured with a real stranger over the real network. Alongside, the phone's embedded daemon stopped answering debug routes in release builds and started refusing any request whose Host or Origin was not local; its gossip intake is deliberately shut entirely for now, which is an interim answer rather than a finished one.

Every hive, channel and friendship in NAOMS is a chain of signed commits. The rule that makes that worth anything is simple: a commit is accepted because its signature verifies against a key that is allowed to write there, not because the message carrying it says who sent it. Today's fixes (2026-09-29, UTC) were four separate places where that rule had a hole, plus two on the phone. This post covers only changes that landed on the main branch, and it ends with what we could not verify.

A device that signed whatever it was handed

The oldest gossip path in the code (a "stripped envelope" handler) accepted a chain commit that arrived without its signature, hash, sequence or timestamp. It then did the helpful thing: it signed the commit itself, with this device's key, under a signer name read out of a field the sender controls, stored it, and rebroadcast it. The effect was that any peer could get your device to author an arbitrary commit as you, including a "member added" commit (6fb41097df1).

The fix deletes that path. An envelope missing any signed field is now dropped, counted as gossip.chain_commit.unsigned_dropped, and logged. The signer is whoever the commit itself names, and every accepted commit goes through the normal signature check.

The commit records a red-first test run: on the old code the tests show a forged commit producing rows and two rebroadcasts where zero were expected (5 failed, 1 passed), and on the new code all 6 pass.

An import path that skipped the check

Gossip was not the only way commits arrive. When a peer pushes a chain you already hold, the import path inserted its commits and materialized them with the signature exactly as sent, with no signature verification and no trusted-key lookup. Any connected peer could therefore append forged commits to an existing hive, channel or friendship chain (75ab6177395).

The fix does not add a second, slightly different checker. It composes the same gates the ordinary ingest path already runs, in the same order, before anything is stored. Three outcomes stay distinct: refused (counted as rejected), parked (the key is not installed yet, so it waits for replay rather than being persisted or counted as landed), and duplicate. The commit message also notes that an older test's fixtures used the literal signature "sig", which means those tests had been passing through the hole; they were rebuilt with genuine commits.

A stranger taking over a friend's network identity

This one is the clearest to describe and the strongest to measure. Before any authentication, the handshake code read two hints out of a raw frame, the sender's claimed from and replyNodeId, and stored them as the network address of that person. For a friend you were already connected to, that rewrote their recorded node id to the sender's node. After that, the sender's node was authenticated as your friend (d0872e62d19).

Per the commit, this was measured with two processes over the real network transport: a stranger with a fresh key and no prior relationship connected and sent one raw frame. On the old code the friend's recorded node id became the stranger's and the stranger's connection authenticated as the friend; on the fixed code the binding was unchanged and the stranger did not authenticate. The unauthenticated path now only seeds the address book, so the handshake reply can still route; the binding itself is updated only on the authenticated path, from the live connection.

Votes that named their own voter

The governance code took the voter's (and proposer's) identity from the payload of the vote instead of from the commit's signer, so a member could vote as someone else, open a proposal in another member's name, or overwrite another member's vote by reusing its response id. The tally also counted approvals from people who were not members at all (dec999f4d77).

Now a named actor is accepted only if the commit signer is one of that actor's identities (their root identity or their per-hive identity; the commit notes that insisting on raw equality wrongly refused honest votes cast under the root name). The tally counts only enrolled voters on the current roster. The older test fixtures signed every commit with one fixed test key and put the voter only in the payload, which is exactly the forged shape, so they were changed to sign as the person they name. Seven tests that fail on the old code pass on the new code (22 of 22 new tests green).

On the phone

Three separate changes hit the phone's embedded daemon:

  • Every route now checks Host and Origin (d3cd60a4df7). The daemon's HTTP surface had sat behind a permissive cross-origin setting with no Host or Origin check, and cross-origin rules hide a response from a web page without stopping the request from reaching a handler. The websocket guard also had a DNS-rebinding hole, because its same-origin case admitted a request whose Origin equals its Host, and under rebinding both are the attacker's name. A guard in front of every route now requires a loopback Host and runs the same origin verdict everywhere.
  • Test and debug routes are compiled out of release builds (8b615904155). Five routes meant for testing (one of which ran arbitrary read-only SQL with the vault's database key, so every table could be read decrypted; another could inject a peer into the live transport) were registered unconditionally and without authentication. The previous commit blocks browsers, but a native app on the same phone dialing the local socket sends neither header. Those routes now exist only behind a cargo feature that is off by default.
  • Gossip intake is shut, on purpose (8a7efe1be99). The phone inserted every gossip chain commit it received, with an empty signature, taking the signer from the message's own from field. This is the same hole as the desktop one above, and unlike the desktop, the phone does not yet have the machinery to verify those commits. The interim fix admits none at all (the allow-list of acceptable commit types is literally empty) and every refusal is named in the log. A real port of signature verification to the phone is filed as the actual fix. The commit itself marks one thing as unmeasured: how bad the original hole was depends on whether the gossip layer limits who can publish on a topic.

Identity that does not leak

The same day continued a larger piece of work: a channel's owner, and the member added by an open self-join, are now recorded under an identity scoped to that channel or hive, not under your root identity (cacca80e571, dd434c7bb80). The channel receipt is the one worth reading: with two real daemons, a scan of the replica of a standalone channel found no root identity in the owner field, the genesis signers, or any body, and three controls (one that proves the scanner can see the scoped identity, one with a fabricated identity that must find nothing, and one that injects the root identity and must be flagged) behaved as expected. Separately, desktop calls now run over a short-lived per-call network endpoint that is only dialed after the peer's advertised identity and certificate verify, with no silent fallback to the persistent endpoint (fef5ed4b898).

What we could not verify

  • The self-join fix's own commit says a live cross-identity join is blocked on its test host by an older, separate signer wall, so its test cannot show a persisted membership row; the evidence there is the real attribution failure before the change, not a full end-to-end join.
  • The channel-owner commit lists a known cost: some older in-process test harnesses that mint a channel with a root creator now fail closed and need the real-signer harness.
  • A device-list feature (announce which devices belong to a member) landed and was reverted the same day. This post does not describe it because it is not in the final state.
  • We have not re-run any of these tests myself. The red and green numbers above are as recorded in the commit messages, not measurements made for this post. This day had several hundred commits; this is a selection of the security-relevant ones, not a complete list.

The pattern across all of it: a claim inside a message (a from field, a payload voter, a raw frame's hint) is an input, not an identity. Each fix moved the decision to something the sender cannot choose, a signature that verifies or a connection that authenticates, and each shipped a test that fails without the change.
