The Governance Socket Is Back

Four small repairs to the standard interface our agents plug into — and why the most interesting one was a security gate that had quietly turned into a blanket 'no'

Technology Architect free June 27, 2026·9 min read·agents
TL;DR Our AI agents don't reach NAOMS's rules and memory through a private back door. They use MCP, an open standard interface. That interface had frayed in four specific places — and the most instructive was a security gate that ran on every tool call, hit a forbidden synchronous database query on the serving daemon, threw, and got the exception swallowed into a generic "capability lookup failed." A gate that should sometimes say no had started always saying no. This is the repair log: four seams, four root causes, and the discipline of keeping a load-bearing standard clean.

Here is a piece of NAOMS that no end user will ever name, and that nearly everything else quietly stands on. When an AI agent works inside NAOMS — checks what it is allowed to do, reads the procedure it should follow next, reaches into memory — it does not do that through a bespoke private channel. It goes through MCP, the Model Context Protocol: an open, standard interface for connecting a model to tools and context. MCP is the socket the agents plug into to reach the system's governance. Session boot, policy checks, every tool call an agent makes — all of it travels this one wire.

That choice is deliberate, and it has a cost. We could have wired our agents to the daemon with something proprietary. We didn't, for the same adopt-the-protocol, don't-reinvent-it reason that runs through the whole project, and which we wrote about at length when we first exposed the daemon's real controls over MCP. The bill for that choice is maintenance. A standard you adopt is a standard you have to keep actually working, because it is load-bearing for every agent action. This week was paying that bill. Four seams had come loose. None was a new feature. All four were the kind of small, specific rot that degrades everything downstream without ever announcing itself.

These were post-ship bugs, filed against the MCP server's own bug register, fixed one at a time. We want to walk through each, because the root causes are more interesting than the headline, and one of them is a genuinely good lesson about where a security check can go wrong.

Seam one: a security gate that learned to always say no

This is the one worth slowing down for.

Every single tools/call an agent makes over MCP passes through an agent-trust capability gate. The gate's job is exactly the trust-the-agent, verify-at-the-server discipline: before a tool runs, check that this caller is actually entitled to that capability. A read-only member should be denied a write tool; a properly scoped agent should sail through. That is the whole point of the gate — it is supposed to sometimes say no.

It had started always saying no. Every tools/call came back with the same flat error: capability lookup failed. Curiously, tools/list still worked fine, which is the clue that cracks the case: tools/list has no capability gate, and every path that did have the gate failed.

The root cause is a beautiful little trap. The gate answered its entitlement question by running a graph query — and it ran the synchronous version of that query. But synchronous graph queries reach into the signer's native code (the FFI layer), and on the daemon isolate that is busy serving the live WebSocket, synchronous FFI calls are forbidden — a guard introduced a couple of weeks earlier throws the moment one is attempted on the serving isolate, precisely to stop that class of blocking call. So the gate called the query, the guard threw, and the throw was caught and dressed up as the generic capability lookup failed. The entitlement check never actually ran. It just looked like a denial.

That is the dangerous shape. A masked exception inside a security gate does not fail loud and obvious. It fails as a polite, plausible "no" — and a gate that denies everything looks, from the outside, almost like a gate working very strictly. It took reading the gate's own code path to see that the "no" was not a verdict at all. It was an error wearing a verdict's clothes.

    A[Agent: tools/call policies.check] --> B{Agent-trust capability gate}
    B -->|asks entitlement question| C[Graph query]
    C -.->|BEFORE: synchronous query| D[Synchronous FFI into signer]
    D --> E[Serving-isolate guard:\nsync FFI forbidden here -> throws]
    E --> F[Throw caught and masked\nas 'capability lookup failed']
    F --> G[Every tools/call denied\nentitlement never evaluated]

The fix was to make the gate honest about its own execution model: the capability check became async, awaits the asynchronous graph query instead of the synchronous one, and the call site awaits it in turn. Thirty-seven existing security tests had to learn to await the gate too. With the change in, we ran a full live flow against the running daemon — an agent calling tools/call for a policy check — and watched it return an actual HTTP 200 with a result. The generic capability lookup failed was gone, and the gate was back to doing its real job: passing the entitled and denying the unentitled, on the merits.

The lesson we are keeping: a verify-at-the-gate check is only as trustworthy as the failure mode behind it. If the gate can throw and have that throw rendered as a denial, then your security boundary and your bug surface are wearing the same face. Make the gate fail loud, or — better — make sure it cannot trip the guard at all.

Seam two: the live path and the replay path disagreed

The second seam lived in the login flow, and it is a clean example of two code paths quietly drifting out of agreement.

When the daemon needs the owner to approve an MCP authorization, it classifies the request by trust tier. A high tier means "you already trust this deeply — show a quiet banner and an approvals card, don't interrupt with a modal." The MCP OAuth flow is supposed to be high tier. On a fresh connection it behaved exactly that way.

But reconnecting was a nuisance: every reconnect popped a full authorization dialog instead of the quiet banner. The reason is subtle. The flow profile that drives this had no tier declared at all. The live broadcast path happened to announce "high" anyway — but when the approval request was persisted to the chain, it wrote the profile's tier field, which was undefined, so the stored record carried no tier. On reconnect, the daemon does not replay the live broadcast; it reads the stored record back and re-broadcasts it. The replay code, finding no tier, defaulted to medium — and medium is not suppressed from popping a dialog the way high is. So the live path said "quiet," the record said nothing, and the replay path filled the silence with "medium," and the owner got a modal every time they came back.

This is the honesty axiom expressed in plumbing: the record on the chain should say exactly what the live moment said, because reconnect trusts the record, not your memory of the broadcast. The fix was small and exact — declare the tier as high on the flow profile itself, so it persists, so replay reads "high," so the banner stays a banner. The general hazard is worth naming: any value that exists implicitly in a live path but defaults differently in a replay path is a latent inconsistency, and reconnect is the precise moment it surfaces.

Seam three: the approval surface is cosmetic, the receipt is load-bearing

The third seam showed up in a live test by the owner. Approving the MCP authorization on a generic surface — a banner, a card, a CLI prompt, anything other than the one canonical popup — resolved the approval on screen, and then nothing happened. The client never got its key.

The protocol underneath is OAuth: the agent is waiting for an authorization code to be delivered to a small loopback callback on its own machine, which it then exchanges for a token. Approving on a generic surface marked the request approved, but it never delivered that code to the client's callback, and the token endpoint kept rejecting the exchange — because the generic grant never minted the signed approval receipt that the MCP OAuth verifier specifically requires. The human said yes; the cryptographic proof that the human said yes was never produced; the agent waited forever.

The repair makes the daemon authoritative about delivery. Now, when an MCP OAuth approval lands on any surface, the daemon resolves the linked authorization code, mints the required approval receipt signature, and delivers the code and state to the client's loopback callback itself, server-side — before the generic resolution path runs. The principle we pulled out of this: which button the human pressed is cosmetic, the signed receipt is load-bearing. A protocol obligation cannot depend on the human happening to approve through one blessed widget.

Seam four: a menu that advertised a dead item

The fourth was the simplest and the least dramatic, and it still mattered. When an agent boots over MCP, it is handed a vocabulary and a conductor procedure that tell it how the lifecycle works. Both still referred to a procedure by an old numbered id — call it the lifecycle's former name — that had been renamed some time earlier. Twelve user-facing strings on the boot surface still pointed at a name that, as a primary id, no longer existed. One of them even cited a supporting doctrine document under the old name, and that document genuinely was not there.

So agents booted against a menu with a dead item on it. We retired the twelve strings to the current name and fixed the dangling doctrine reference. We kept the old name alive as a legacy alias, so any agent or tool that still asks for the procedure by its former id resolves correctly — retiring the advertisement is not the same as breaking the back-compat lookup, and we wanted only the first.

One honest caveat here, because it is exactly the kind of thing that is easy to overclaim: this fix is in the governance seed, and the seed is applied once, at a daemon's genesis. A freshly onboarded daemon picks up the corrected strings immediately. The long-running production daemon reads the menu it was seeded with, so it will keep showing the old name until an owner-gated re-seed. The code is correct on origin/main; the live surface there is not yet updated. We would rather say that plainly than imply a deploy that hasn't happened.

Why "use the standard, and keep it clean" is the actual feature

None of these four was a new capability. They were repairs — closing seams on an interface that had already shipped and then frayed at the edges. It is tempting to file that under unglamorous and move on. We think it is closer to the heart of the project than that.

The reason to adopt an open protocol instead of inventing a private one is that the protocol outlives any single implementation, and anyone can speak it. The price of that reason is a standing duty: the standard interface has to keep working, on the merits, every day, because it is the one wire every agent action runs through. A capability gate that masks its own errors as denials, a trust tier that disagrees with itself across a reconnect, an approval that depends on the right widget, a boot menu that names something gone — each one, left alone, would have produced a hundred quiet, hard-to-diagnose failures downstream and never once shown up as a clean alarm.

The governance socket is serving cleanly again. The gate evaluates entitlement instead of swallowing an exception. The reconnect honors the tier it was given. The key is delivered no matter which surface said yes. And the boot menu, for freshly seeded daemons, finally lists only things that exist. That is the work a system that means to last has to be willing to do without applause — keeping the plain, load-bearing standard honest enough to trust.
