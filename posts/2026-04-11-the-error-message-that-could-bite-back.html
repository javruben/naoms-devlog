The Error Message That Could Bite Back

How 'just show the error' quietly becomes a way in for an attacker — and why the fix is boring on purpose

Process Confession free April 11, 2026·4 min read·clients
TL;DR A confession: the riskiest bug we found that week was hiding in the most innocent line in the app — the part that shows you what went wrong. Here's how a helpful error message can be turned against you, and the dull fix that closes the door.

Some bugs hide in the clever code. This one hid in the most boring, well-meaning line a UI can contain: the part that shows you what went wrong.

On Saturday 2026-04-11 — the quietest day of the week, the critic-sweep day — the review pass surfaced a top-severity bug in the browser client. Not in the crypto, not in the chain logic, not in any of the places we'd been watching. In the error display.

What it was

When a request failed, the client did the obvious, helpful thing: it took the error and put it on the screen so you could see it. The implementation dropped the error's message text straight into the page as live markup — error messages from a failed request could carry an injection vector, and we were rendering them as HTML.

Here is the quiet trap. An error message feels like trusted text. It's coming from your own code, your own failure path, your own catch block — it feels like a string you wrote. But error messages are not always strings you wrote. They can carry fragments of a failed request, a server response, a value that originated somewhere you don't control. The moment any of that gets rendered as markup, the browser stops treating it as text and starts treating it as structure. Text that was supposed to describe a problem becomes text the browser will happily execute as structure. That is the whole shape of the vulnerability, and we will not be writing out a working payload here — the class is the lesson; the recipe is not.

We want to be honest about how this happens, because it is not exotic. Nobody sits down and writes "inject the user's error into the page as live HTML." You write "show the error to the user," reach for the convenient property that renders a string as markup because it's the one you reach for, and the gap between display this text and render this markup is one method name wide and completely invisible in review unless you're looking for it. We weren't. The critic was.

The fix is boring, and that's the point

The fix has no cleverness in it at all. Stop assigning the raw markup property. Build the elements explicitly, and put the untrusted text in through the property whose entire job is "this is text, render it as text, never as markup." Where the message genuinely needs a link, construct the link element explicitly rather than splicing a string and hoping. The text property cannot be tricked into executing anything, because it does not parse. It is the boring, safe, slightly-more-verbose path, and it is correct precisely because it refuses to be clever.

The lesson we keep relearning: in a browser, the dangerous default is the convenient one. The markup-rendering property is shorter to type and it is the wrong answer almost every time untrusted data is involved. The text-only path is a few more characters and it closes the door the convenient one leaves open. Choosing the boring one is not paranoia. It is just declining to hand the browser a parser it didn't need.

The two it traveled with

The same fix cleaned up two smaller siblings, and they rhyme with the main bug in a way worth naming. Both were swallowed errors: one failure path in the chain queue silently discarded its errors; another, in signer crash recovery, had only a comment where the handling should be. A failure handler that does nothing is a promise to handle failure that the code never keeps. The fixes added real logging with context, so the next failure leaves a trace instead of vanishing.

The injection bug and the swallowed failures are the same mistake wearing two costumes: trusting that something is safe because it's yours. Your error message must be safe because you wrote it. Your async failure must be benign because you put a handler there. Neither assumption survives contact with a critic that actually reads the code.

Why we're telling you

Because the worst bug of the day was in the helper, not the headline. We had spent the week on governance architecture and chain-write paths and re-encryption — the parts that look security-critical — and the live injection vector was sitting in the function that shows an error toast. Security bugs do not respect your sense of where the important code is. They live wherever untrusted data meets a powerful default, and rendering a string as markup is the most powerful default in the building.

The critic found it on a quiet Saturday, behind the line, before any user ever typed a request that failed in an interesting way. That is the best possible place to find it. Show the error — yes. Just never let the error decide what the page is made of.
