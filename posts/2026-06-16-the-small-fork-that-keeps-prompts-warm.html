Keeping a warm prompt across a restart

In praise of a close fork of llama.cpp that saves a model's prompt checkpoints beside the cache they belong to, and the launcher that makes it a pleasure to run

Technology Fellow Travelers free June 16, 2026·9 min read·local-ai
TL;DR Ask a second question about a long document and the model should not have to read the whole thing again. A small fork of llama.cpp puts that saving on disk, and this is our thank-you to the person who wrote it.

We run our local models on llama.cpp, with one person's work in between: Lumina Nao. Two of their repositories on Codeberg are the subject here — llama-hdd.cpp, a close fork of llama.cpp, and llama-launcher, helper scripts for building llama.cpp and running its server. This piece is the thank-you we owe.

Start with what they stand on, because honouring a fork means honouring its parent. llama.cpp is the C++ project that made running large language models on ordinary hardware normal, and it is generous engineering by any measure: fast, portable, MIT-licensed, and moving quickly. Much of what follows is careful work laid on top of that.

The gap they noticed

When a model reads a long prompt it does not merely read it — it encodes it, turning the tokens into the internal state it will consult for the rest of the conversation. That work is called prefill, and on a long prompt it is the expensive part. Ask five questions about the same long document and, done naively, you pay for that encoding five times.

Servers avoid this by keeping the encoded state in a slot — one conversation's working memory inside the server — and reusing it on the next request. llama.cpp's server can also write a slot to disk, so the state survives a restart. Alongside that encoded state, each slot holds a second structure: a list of checkpoints, snapshots of the parts of the cache that cannot simply be rewound to an earlier position. Some model architectures lean on those checkpoints to reuse a shared prefix without paying for a cold prefill first.

Upstream's disk save writes the cache. The checkpoint list stays in memory. So on those architectures, a slot brought back from disk arrives without the thing that made reuse possible, and re-prefills from scratch anyway — defeating the point, as the fork's README puts it.

There is a reason someone would care enough to fix that, and it is written down in their own words: on machines where system memory and graphics memory are the same pool, holding those checkpoints in RAM competes with the model weights for the one resource you have least of. This is a fix born of running big models on a single box and feeling the squeeze.

What they built, and what they left alone

The answer is a second file, and that restraint is the craft. The fork writes the checkpoint list to a companion file beside the cache — the same filename with .ckpt on the end. Eight fixed bytes identifying the format first, then a count, then each checkpoint's position range, token count, and the checkpoint state itself: the part upstream's slot save leaves behind. Upstream holds that list in memory; the fork is what puts it on disk.

Nothing has to be switched on. A server already started with a slot directory gets the companion file on its next slot save, which is how the README describes it too: automatic and transparent, no flag changes. A feature you have to go and enable is a feature most people never get, and they chose the version where everyone already saving slots gets it.

The fork adds exactly one flag of its own, off by default — a dial that thins how many checkpoints a save writes. Change nothing and every checkpoint is written. Turn the dial down and the list is thinned with geometrically growing gaps measured back from the newest, keeping the newest and the earliest. The shape of that rule is lovely. If your next prompt diverges from the last one near the end — which is what a follow-up question is — there is a checkpoint close by and you re-encode very little. If it diverges further back, the nearest surviving checkpoint is further away and you re-encode more, in proportion to how far back you went. And the thinning applies only to the copy going to disk; the checkpoints a running server is holding are left exactly where they are.

Failing soft, on purpose

The loader is the part we admire most, because each way it can fail was thought about separately.

If the companion file is missing, it returns zero and the server carries on with an empty checkpoint list. If the file is there but its first eight bytes are not the ones the fork wrote, it says so in the log — "invalid or stale checkpoint sidecar" — and does the same. If the file runs out partway through, it clears whatever it had already parsed rather than handing back half a list. Every one of those paths costs the same thing, the checkpoints and the prefill they would have saved, and none of them costs correctness. None of them stops the server.

The signature check is the quiet hero. It would have been easier to read whatever was there and hope, and a stale file from an older format would then have been loaded as though it were current. Instead the file has to say what it is, and if it does not, it is refused out loud.

We have a name for that instinct. Honesty is one of the three ideas this whole system is built on: no silent mutation, no silent drop, and never report a thing as done when it is not. Finding it already written into a stranger's loader, with the reasoning spelled out in comments for whoever reads it next, was one of the better mornings we have had reading someone else's code.

The discipline of staying small

Anybody can fork a fast-moving project. Keeping the fork small, current and mergeable is the unglamorous half, and it is the half this one is built around. The README sets the terms in a sentence — it tracks upstream closely, and the divergence is a small set of patches centred on the sidecar feature — and the policy underneath says the main branch tracks upstream, upstream is merged in regularly, and fork-specific bugs come to the fork while everything else goes to llama.cpp.

You can see the same long horizon in the details. The fork highlights the checkpoint and slot save/restore lines in the log, and it picks them out by matching the text of each message rather than the level-and-function prefix in front of it, with a comment explaining that llama.cpp's prefix format changes upstream. That is a person writing today's convenience so that it survives next year's rebase.

And the offer is standing. The same sidecar is proposed upstream as a pull request against llama.cpp, written out in full, format and all — and it answers a feature request somebody else had filed there months earlier. It is open, not merged, and it may stay open for a long time; that is how upstreams work. But the work was done in public, offered to the project it came from, and left on the table for whoever wants it. That is the opposite of the fork that quietly becomes a private codebase.

The launcher is hospitality

The launcher is the other half of the pair and a different kind of gift entirely: an interactive installer, a build script for the backends it targets, per-model tuning files, launch history so you can rerun what you ran last week, and benchmarking and stress scripts. It is the accumulated knowledge of actually living with this software, written down so the next person does not have to rediscover it.

Two touches say the most about who it was written for. Its README's flag table, on the disk-cache row, names the fork and says what it would add — a signpost planted in a table of options. And there is a whole page in that repository devoted to explaining what a single tuning flag really does, with a latency table and sizing guidance, which opens by saying plainly that it exists because the flag's name is misleading and has led to repeated mistakes.

Underneath the conveniences sits the question of what to delete when the disk fills. The launcher's proxy keeps each conversation on its own slot file, keyed by a session identifier when the client sends one, and saves and restores those files around session switches. Before each save it checks free space and the total size of the slot cache, and while either is past its limit it retires the oldest slot file together with its checkpoint file, excluding the session being saved and the one about to be restored, so a cleanup pass cannot take the slot it is about to write or the one it is about to read. The mechanism lives in the fork; the policy that lets you leave it running lives here. Each README points at the other, which is all the coupling either of them needs.

What we run, and what we checked

We build the fork from a pinned revision and run our local models against it. Because its server speaks the same HTTP shape as most others in this space, we did not have to teach our code a new protocol: our one door for every model you run already carried the call, and we add two optional fields to it — one asking for the prompt cache, one naming the slot to reuse — when a caller has marked a conversation worth keeping warm.

We did check whose build we were running. A check we run against the slot directory opens the file the fork writes and reads its first eight bytes, and they were the fork's own signature — three hundred megabytes of checkpoint state sitting beside the cache it belongs to, exactly as documented. Stock upstream writes no such file at all. The mechanism was there, on disk, in bytes we could name.

Where to find it, and how to say thank you

Both repositories live on Codeberg, and that is the part to get right if you want to help: each has a read-only mirror elsewhere, and both READMEs ask for issues and pull requests on Codeberg instead. Both accept them there. The fork carries upstream's own MIT notice unchanged. Bugs in the shared C++ belong upstream at ggml-org/llama.cpp; the companion file, the thinning rule and the log colouring belong with the fork.

So: thank you, Lumina Nao. A loader that refuses to guess, a thinning rule whose cost tracks how far back the prompt changed, and a launcher that reads like it was written for somebody else's benefit — and today, ours. Your work is in our product, and we are glad you built it.
