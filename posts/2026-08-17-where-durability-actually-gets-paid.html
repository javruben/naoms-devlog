Where durability actually gets paid

A signed, hash-linked log is the record that has to survive a power cut; the tables you actually read from are rebuilt from it — which changes what the database underneath has to promise, and what that promise costs per write

Technology Architect free August 17, 2026·7 min read·storage-sync
TL;DR What NAOMS records goes first into a signed, append-only log, and the tables you read from are rebuilt out of that log rather than being the original. That splits your storage into what must survive a power cut and what merely has to be reproducible — and it lets the database underneath stop flushing to disk on every single commit.

The question a storage layer has to answer

Pull the plug on a machine mid-write and something is lost. The interesting engineering question is not whether — it is which layer promised it would not be, and what that promise cost on every write leading up to the moment nothing went wrong.

Most software delegates the whole question to its database, and the database answers it with a single system call: fsync. An ordinary write hands bytes to the operating system, which is free to hold them in memory and write them out when convenient; a power cut takes whatever was still in flight. An fsync is the instruction that says stop here, and do not return until the storage device confirms these bytes are physically down. It is what converts "the program handed the bytes over" into "the bytes are on the disk", and it is slow in a way nothing else in a small write is slow: the work itself is microseconds, and the wait is milliseconds.

Databases commonly pay it on every commit by default. That is a good default, and it is a default made without knowing anything about what is written above it — and what is written above it is the whole subject of this piece.

What NAOMS actually writes down

Everything meaningful here is recorded first as a commit on a chain: an append-only sequence of entries, where each entry carries a hash of its own content, the hashes of the entries it follows, and a signature from whoever wrote it. Nothing is edited in place. A correction is a new entry that supersedes an earlier one, and the earlier one stays where it was. That is the one idea underneath everything else here.

The screens you actually look at are not reading that sequence. Reading a hash-linked log to answer "what are this person's contacts" would mean walking the whole thing every time. So the log is folded, entry by entry as each one lands, into ordinary indexed tables — a projection, in the sense of a view projected from a source rather than the source itself. That is the write to the log, read from the projection inversion, and it has a consequence that is easy to state and easy to under-use:

The projection is not data. It is a function of data.

Which means it does not have to survive anything. It has to be reproducible.

That distinction is only worth as much as the replay code behind it, so here is the replay code. There is a routine that takes a chain, loads its commits — across its branches, not one of them — in a deterministic order, and folds each through the same logic that folded it the first time — rebuilding the derived rows from the commit rows. It is not a private helper: it is registered as a tool the system can be asked to run, and it reports back how many commits it replayed. It skips entries that were deliberately erased or archived, because a rebuild that resurrects something you deleted is not a rebuild.

It is also code with a scar on it, and that is the part worth showing. An earlier version rebuilt only one of the branches and reported success. The comment above the fix says why that was treated as a correctness bug rather than a missing feature: a partial rebuild presented as complete is an Honesty-axiom silent-incompleteness. A rebuild you cannot trust to be total is not a rebuild you can use to relax a durability guarantee.

What that buys, and what it costs

If the derived rows are reproducible from the log, then what the database has to be careful about is narrower: the commit rows themselves. And it can be careful about those in a cheaper way than flushing on every commit.

The setting is applied at the moment the database connection is opened, and it is two instructions. The first puts the database in write-ahead log mode: changes are appended to a separate ordered file and folded into the main database file at intervals called checkpoints, rather than being written into the main file as they happen. The second sets how often that ordered file is forced down to the disk. Ours is set so that the flush happens at checkpoints rather than on every commit.

SQLite documents that combination as safe from corruption, and the mechanism behind that word is worth being precise about, because it is doing the load-bearing work here. The ordered file stays ordered. A power cut truncates it at some point, and what is on the near side of that cut is a whole number of committed transactions — not half of one. So the outcomes SQLite documents for this mode are the last few committed transactions are missing and nothing is missing. A database file left internally inconsistent is not among them.

For a log of hash-linked entries, "the last few are missing" is a mild outcome in a way it would not be for a mutable table. A truncated append-only log is a shorter append-only log. An entry that is still there still hashes to what it says it does and still carries the signature it was written with. Nothing has been left half-edited, because nothing was ever edited.

Here is the cost, stated plainly, because it is real. If your machine loses power at the wrong instant, the most recent committed entries can be gone, and they are gone from the log itself — the log lives in the same database file as everything derived from it, and the replay described above rebuilds derived rows from commit rows rather than recovering commit rows. What the replay covers is the other direction: derived rows that fell behind the log, which is the likelier state after a hard stop, because folding a commit into the tables happens after the commit is recorded rather than inside it.

The stricter behaviour is still available. The mode is read from a setting at connection time, and the value is matched exactly as one of three words — FULL for a flush on every commit, NORMAL for the default described here, and OFF. If a machine sits somewhere with unreliable power, FULL is the one to set.

What the flush was costing

The numbers below are one measurement on one machine — a laptop with an Apple filesystem, profiled in May 2026 — and they are itemised in the source rather than summarised, which is why they can be quoted at this resolution.

A single signed append cost about 80 milliseconds, and that figure is dominated by waiting rather than by cryptography. Broken out: the threshold signature itself about a millisecond, the round trip to the separate process that holds the signing key about another, the commit-time flush between ten and twenty-five, the checkpoint flush another ten to twenty-five, and the work that runs after the commit — folding into the tables, telling other devices — anywhere from ten to fifty.

The change described here removes exactly one line of that list: the commit-time flush. The absolute saving is the honest figure — roughly ten to twenty-five milliseconds off a signed append. The checkpoint flush is a separate, explicit instruction and still happens. As a percentage it depends entirely on which write you are asking about, and the answer is different for a write whose budget is not 80 milliseconds, which is why the absolute number is the one worth carrying.

Two milliseconds of that 80 are cryptography. It is worth sitting with that ratio for a moment if your mental model of "this is signed, so it must be slow" was formed anywhere other than a profiler. The expensive part of writing a signed record was not signing it.

The part that generalises

The reason any of this is allowed is not a tuning trick. It is that the system had already answered, structurally, a question most systems leave to their storage layer: which of the things it writes are original, and which are derived?

Once that line is drawn and the replay behind it is real and total, the two sides can be given different promises. Originals get durability. Derivatives get reproducibility. Paying for durability on both is not wrong — it is correct, and it is invisible, and it is one of the few kinds of cost that a profiler will show you without ever telling you it was optional.

The check to run against your own storage is small: pick a table, and ask whether you could delete it and get it back. If you could, ask what your database is currently promising about it, and whether anything upstairs is relying on that promise. If you could not, you have found the thing that has to survive — and it deserves the expensive guarantee, undiluted, precisely because fewer things are asking for it.
