Revoke Access, and It Stops Handing Out Keys

There was a narrow window where an app you had just revoked could still ask 'am I approved yet?' and be handed a fresh, working access key. We closed that one window: the approval check now consults the revocation record, fails closed if it can't, and hands out nothing. This seals one specific leak — the larger revocation story is still ahead of us.

Technology Architect free July 5, 2026·5 min read·consent-security
TL;DR Say you install a plugin, grant it access, then change your mind and revoke it. You would expect that revocation to bite immediately. Until this week, one specific back-channel didn't get the message: the very next time that app asked "am I approved yet?", the system would still mint and hand back a fresh, working access key. We closed that window. The approval check now consults the revocation record — the same one the token validator already used — refuses to hand out anything for a revoked grant, and fails closed if it can't even complete the lookup. This seals one concrete leak. It does not mean revocation is fully solved: actively withdrawing an already-installed app's stored credentials, with a tamper-evident audit trail, is real work still ahead.

A revocation that leaves a back-channel quietly handing out keys isn't a revocation. It's theater.

That sentence is the whole reason this small change was worth doing loudly. Most of what we shipped this week fits in a few lines of code and closes exactly one gap. But the gap sat on a load-bearing promise — that when you say "no more," the system stops — and a promise with one silent exception isn't the promise you thought you had.

The window

Here is the flow, in plain terms. You install an app or plugin. It asks for access. You approve it. From then on, the app periodically checks back — "am I approved yet?" — and when the answer is yes, the system derives a fresh working access key for it and hands it over. That polling check is how a newly approved app picks up its credentials.

Now suppose you revoke that approval. You've changed your mind; the app should be cut off. What actually happened, until this week, is that the are-you-approved check didn't notice. It looked at one thing only: did the original approval request say "granted"? It did — and revocation never changed that. So the next time the just-revoked app polled, the check saw "granted," derived a fresh access key, and handed it out. A revoked app could still get credentialed, inside the narrow window between your revocation and the app's next poll.

The reason is a design decision that is correct everywhere else in the system: we never rewrite history. When you revoke an approval, we do not reach back and flip the original "granted" request to "denied." That original request is a signed, immutable record of something that genuinely happened — you did grant it, once. A revocation is written as its own separate record, layered on top. The truth of "granted then revoked" is the two records together.

Which means any code that asks "is this app allowed?" has to read both records. The token-validation path — the one that checks credentials an app already holds — already did. It consulted the revocation record every time. But this second door, the are-you-approved poll, was only reading the first record. It trusted "granted" and never asked whether a revocation had landed since. Same question, two doors, and only one of them was locked.

What changed

The fix is to lock the second door with the same key the first one already used.

Before the poll's "granted" path derives and returns an access key, it now consults the revocation record — the exact same revocation check the token validator uses, not a new bespoke one. If the grant has been revoked, the check returns "revoked" and hands out nothing. The short-lived secret it was holding in memory to build that key with is discarded rather than left lying around.

The part worth dwelling on is what happens when that revocation lookup can't be completed at all — a partial or unavailable record, a lookup that errors out. The path does not shrug and fall back to "well, it said granted, so here's your key." It fails closed: no answer means deny. It drops the secret and returns "revoked." The reasoning is strict and, we think, correct — if the system cannot prove a grant is still live, it must not act as though it is. An unprovable grant is treated as a revoked one. That is the Honesty axiom applied to authorization: refuse rather than guess in the permissive direction.

It ships with two tests that are the point of the exercise, not decoration. One proves the ordinary good path still works: a genuinely granted, never-revoked app still gets its access key on the poll, exactly as before. The other proves the hole is closed: a granted-then-revoked app now gets "revoked" and nothing else. That second test was written to fail against the old code first — and it did, handing back a working key for a revoked grant — before the fix turned it green. A guard you never watched fail is a guard you can't trust.

  A[You grant an app access] --> B[App periodically asks: am I approved yet?]
  B --> C[You revoke the grant · recorded as its own separate entry]
  C --> D[App polls again: am I approved yet?]
  D --> E{Approval check}
  E -->|OLD behavior| F[Reads only the original request · still says granted]
  F --> G[Mints a fresh working access key · hands it over]
  E -->|NEW behavior| H[Also consults the revocation record · same gate the token validator used]
  H --> I{Revoked, or lookup cannot complete?}
  I -->|yes / cannot prove otherwise| J[Return revoked · discard the secret · hand out nothing]
  I -->|no, provably still granted| K[Mint the access key as before]

What this is — and, honestly, what it is not

This closes the specific revoke-then-poll window where a just-revoked app could still be handed a working key. That window is now shut. If you revoke a grant, the next poll gets nothing.

It would be easy — and wrong — to let that read as "revocation now works." It doesn't, not fully, and pretending otherwise would be exactly the kind of quiet overclaim this system exists to refuse. The larger capability is still ahead of us: actively withdrawing an already-installed app's stored credentials — the ones it's already holding — and writing a tamper-evident audit event when you do, so there's a durable record of who was cut off and when. There is no production code for that yet. The parent effort that would deliver it is still on the backlog.

So the honest headline is narrow on purpose: we sealed one concrete leak in the approval-polling path. We did not ship revocation-as-a-whole. Those are different sentences, and we're only entitled to the first one.

We're telling it this way because default-deny and revocation that actually bites are not features you bolt on at the end of a consent-first system — they are the system. Every place where a "no" quietly fails to propagate is a place where consent was decorative. This was one such place. It's closed now. There are others still to find, and we'd rather name the ones we haven't reached than let a single green check stand in for a promise we haven't finished keeping.
