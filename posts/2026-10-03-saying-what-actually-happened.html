Saying what actually happened

This post covers 2026-10-03 (UTC). It is built from the commit messages and diffs that landed on the main branch that day; we did not re-run the tests it mentions, and the last section lists what we did not check.

The common thread: in several places the software said, or assumed, more than it had verified. Each fix below makes the behaviour match the claim, or the claim match the behaviour.

Dialogs that describe what the code does

NAOMS keeps each relationship between two people as a chain: an append-only, signed log of events that both devices hold a copy of and reconcile with each other (this reconciling is called sync). Revoking a connection means appending a "revoked" event to that log. Nothing is sent to the other person directly; the event travels when the two devices next sync.

The confirm dialog used to say the connection "cannot be undone" and that "the peer will be notified". Neither was something the code had established. The new text says that we record the revocation and send it to them the next time the devices sync, and that the revocation stays on record (5da3258cd9f). The same day, the message shown after asking a friend's device to delete data you shared now reports whether the request went through, not whether the other device deleted anything (f4c92a60b59).

A related fix is in the handler behind the revoke button. If a contact's chain id was not known yet (it can lag just after pairing), the append router would have chosen a chain on its own: possibly another friend's, or a freshly created stray one. The handler now refuses with a plain "not ready yet, try again" message (bb28aaa0771).

A third copy change concerned a privacy claim. A card made for one group (a hive, a shared space of devices and people) was described as "unlinkable". The commit message explains why that was too strong: the card is tied to the group by a commitment computed from your root identity and the hive id, so someone who already holds your root identity can recognise it. The copy now says strangers cannot link it to your other cards, and that people who already know you may be able to recognise you (98a7d5297e2). That commit records that its test receipts were to follow on a separate build machine.

Reading your email without changing it

The email adapter imports mail over IMAP, the standard mailbox protocol. Reading a message the usual way marks it read on the server, so every imported message would have appeared as read in your other mail clients. The import now opens folders in a read-only mode (EXAMINE) and fetches message bodies with a variant (BODY.PEEK) that does not set the read flag (cff44ee1ed9).

Decoding also changed. Mail bodies travel in an encoding (such as quoted-printable or base64) and a character set, both declared in the message. Two bugs: single-part bodies were always treated as quoted-printable, and quoted-printable bytes were turned into characters one byte at a time, which turns the UTF-8 pair for "é" into "Ã©". Bodies are now decoded by their declared transfer encoding (69882bbc775), then bytes are decoded using the declared character set. Subject and address headers in the encoded-word format are decoded as well, where before they were not decoded at all (151327ca1b3). The commit messages show failing-then-passing runs for these; we did not reproduce them.

A listing is a pair, not a name

The marketplace lists apps that people publish. A listing used to be looked up by its id alone. But two publishers can declare the same id, and the index keeps both, so "the first entry with this id" depended on which was indexed first.

The identity is now the pair (id, verified publisher), where the publisher is the signer of the release, and only when that signer also signed the original genesis (first) entry. Adopting a listing resolves the exact entry you clicked and refuses by name if the claim is missing or does not match; the storefront shows a badge when an id is claimed by another publisher (64be7efba07). Pictures follow the same rule: one listing's pictures no longer come back "unavailable" because someone else's entry was indexed first (66813dd26d2), and a listing without a verified publisher shows no picture at all (b94aefd02ae).

Revoked devices and live calls

Revoking a device means telling the rest of your system that its key must no longer be trusted. Calls complicate this, because live media (audio and video frames) flows directly between devices, outside the normal event log.

Two changes landed. First, when one of your own devices is revoked, it is now removed from live call media in three places: frames are not sent to it, frames arriving from it are dropped before they are parsed, and it is evicted from sessions in progress. If the system cannot read the revoked-device list, it treats the device as revoked for media rather than guessing (c8da7523a14).

Second, a friend's revoked device could previously still start a one-to-one call, because that signalling is identified by network address. Now, when you revoke your own device, a signed notice goes to each friend carrying only a hash that commits to the relationship and the address. The receiver accepts it only from a party to that friendship and then refuses that address on every admit (89cc58b9564). The commit lists its scope: friendships created before per-relationship signers are refused by name rather than half-handled, and the author flagged the exact scope for a later review.

Checking an update again before it goes live

A restart-required update is verified when it is staged, then waits on disk until the next boot, where the new files are swapped in. The commit that tightened this describes the gap: the staged files could be edited in the meantime, and the check on the running install did not cover them. The boot-time swap now confirms the staged folder lies inside the staging directory, verifies the folder against its own signed manifest right before the swap, requires the signed version to match the pending one and not be lower than the running one, and verifies the live path again after the rename, restoring the backup if that fails (f4f11b39840). A follow-up closed two cases where an unknown version used to skip the checks; unknown now means refuse (5db89ed8e4f).

Smaller fixes with the same theme

  • When an approval lookup fails (the record is unreadable), five places used to turn "I could not read it" into a default action, such as skipping a step-up, marking a code used, or deleting a pending item. They now distinguish found, absent and lookup-failed (586135cbb14). A revoked approval now reads as revoked everywhere, and fails closed when that check errors (e5284df6cf8).
  • On Android, six on-device ML capabilities used to return placeholder text such as "[stub: ...]" as if it were a result. They now return an "unavailable on this platform" error by name (126d0a8613d).
  • Vault secrets with two parts (like a card number and CVV) are stored as JSON, not joined by a pipe character, so a secret containing a pipe is no longer split wrongly (1c1f5ab9a04).
  • A network send now has a single 60 second deadline, so a stalled peer fails with a named error instead of waiting for the longer idle timeout (faf4a2f87d3).

What we did not verify

  • We read commit messages and diffs; we did not run any test or build, so every "red then green" statement is the authors' record, not our measurement.
  • The call-eviction and friend-device changes are about our own devices and friendships; the commits themselves say other hive members are separate work.
  • Some of the above carries stated interim limits: the unlinkable-wording fix recorded that test receipts would come later, and the Android ML features are refused, not implemented; the commit says a real implementation needs an owner decision about a new dependency.
  • We did not check whether any of these changes have shipped in a released build, only that they landed on main on this date.
