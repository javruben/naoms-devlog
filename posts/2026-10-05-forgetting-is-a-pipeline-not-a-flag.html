Forgetting is a pipeline, not a flag

Erasing a shared item means chasing its derived copies: the search index, the vector tables, the graph edges, even a write already in flight. Today's landed work made that erasure transactional per item and made refusals audible. A smaller change made a slow developer check about 21 times cheaper in rule time.

TL;DR This post covers 2026-10-05 up to about 06:00 UTC, the latest commit being a990e989157 on main at the time of writing. The main change: the right-to-forget path now erases a shared item from its search index, its four vector tables and its graph edges inside one transaction per item, refuses to hand erased content to the embedding step, and reports a refused write as refused. This post covers 2026-10-05 (UTC) up to roughly 06:00 UTC, the moment of writing. The newest commit on main that it accounts for is a990e989157 (a comment-only change; the last substantive one is 8603b708d96). Work that lands after that will be in a later post.

Two substantive things landed in this window. One is about privacy, one is about developer tooling. The first is the one worth your time.

How erasure is supposed to work

NAOMS lets a person share something (a message, a photo, a note) and later take that share back. Taking it back is a right-to-forget operation: the content must become unreachable, not just hidden in the interface.

To see why that is more than one DELETE, you need the shape of the data. A piece of content is stored as a graph node: a row with properties, a label, and edges connecting it to other nodes. Around that row we keep derived copies so it can be found:

  • a full-text search index (FTS), which maps words to the nodes that contain them;
  • vector tables, which store an embedding, a list of numbers an AI model computes from the content so that "similar" things can be found by distance. We keep one for text, one for metadata, one for image content (1024 numbers) and one for faces (128 numbers).

An embed queue feeds those tables: a background worker takes a node, asks the embedding model for numbers, and writes them.

So "forget this node" means: remove it from the search index, remove its vectors from all four tables, remove its edges, blank its label and properties, and mark it deleted. The order matters, and so does what happens when one step fails halfway.

What was wrong

A review of the erasure path measured six defects (b0e3a8626f2). In plain terms:

  • The node's label was left in place, so the human-readable title survived erasure.
  • Properties were redacted before the item was removed from the indexes, and the vector rows were kept.
  • Edges were not touched at all.
  • The commit record was marked erased before the node, with no transaction around the two, so a failure in between left an orphan that could not be retried.
  • A failure to remove an index entry was reported as a successful erase.
  • The check that asks "is this node still alive?" before embedding it failed open: if the question itself errored, the node was treated as alive and embedded anyway.

How it was fixed

Per node, one transaction (b0e3a8626f2): remove the node from the search index and all four vector tables first, delete its edges, and only then run a single update that redacts the properties, sets the label to NULL and marks the node deleted. If any step fails, the node rolls back whole, and the failure is returned by name (which node, which table, which error). The share erasure then throws an "incomplete" error and leaves its commit active, so a retry starts from a consistent state. The liveness check now fails closed: when it cannot tell, it refuses to embed.

Review kept finding the next gap, which is the useful part of the story.

A race. The liveness check runs before the embedding model is called, and the model takes time. An erasure landing during that wait had its vectors re-created, because the write afterward was an unconditional insert. The first fix made each insert conditional on the node still being alive, in the same SQL statement (9463d2577d4). Review then found three more writers with the same flaw (a backfill job, a re-embed sweep and the companion writer), so 775bdbe78f2 moved every vector write into one helper, and a pin test scans the source tree to make sure no raw insert reappears. A pin test is a test whose job is to fail if someone later bypasses the design; this one was checked by deliberately adding a raw insert.

A refusal that looked like success. Once the guard could refuse a write, callers that did not read the result still counted it as written. The photo analysis route reported vectors written that were never stored, and the face code logged "wrote" and clustered a descriptor that was never saved (b32de0129a9). The helpers now read back whether a row exists, and a refused image-vector write throws. The route then answers honestly: ok: false if any write was refused and partial: true if some landed (8603b708d96).

A gate that did not cover faces. Before, only the photo node was probed for liveness; the face node was not. It now has its own gate, with a cap of 100 requeues per item, after which the item is dropped with a named error and counted (b32de0129a9, 8603b708d96). A liveness probe that itself errors now requeues the item and counts it, instead of consuming it as refused.

A health endpoint that said too much. The runtime exposes /health metrics without authentication. The new erasure counters there are counts only, with no node ids or database error text, and a pre-existing search-index block that carried a node id and raw SQLite text was reduced to counts and timestamps (775bdbe78f2, b32de0129a9). The test asserts over the whole response body, not one field.

A smaller change: a check that skipped the slow tier and said so

naoms check runs rules grouped into tiers. The nightly tier is meta-rules that walk the whole repository's history. Measured on a three-file package, a bare manual run took about 333 seconds of rule time, and about 286 seconds of that (95%) was the nightly tier; one history-walking rule alone timed out at 138 seconds while finding nothing (a0878b0df55). The commit and advisory tiers took about 7 and 6 seconds.

The first version made every bare manual run default to commit plus advisory, with the same verdict (0 critical, 4 warnings) in about 50 seconds of wall time and about 14 of rule time. Its author then found that the claim "all gates are scoped to the diff" was false for two gate invocations that run the whole repo, so 1843417ee47 narrowed the default to a manual run on one named package, with no --diff or --ratchet. Gate paths keep running every tier. The skip now prints a count: 60 rules skipped, 34 of them critical meta-rules, plus the exact command that includes them. Moving the per-commit gate itself to a lighter tier was explicitly left as a separate decision for the owner.

What we did not verify

  • We read the commit messages and diffs; we did not run the code. Test results we mention are those the commit messages record, and we did not re-run them. Those messages also record failing tests that fail identically before and after the change.
  • There is no automatic retry yet for an incomplete erasure, and nodes erased before this change are not backfilled.
  • Text already inside an in-flight embedding call cannot be recalled, and image bytes read after the liveness statement are outside this change. Blob erasure is a separate tier.
  • The check-default change was measured on one package; the 21-fold figure is for that package, not a general figure.
