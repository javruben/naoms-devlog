The Edge That Only Ever Pointed at One Person

A membership query that confidently returned one name was hiding a message leak that reached every connected peer

Process Confession free April 23, 2026·6 min read·messaging
TL;DR We had a "who is a member of this chain?" query that, for most chain kinds, silently returned exactly one person — the creator — and called it the whole membership. The bug it was hiding was a P0 broadcast leak: messages on un-migrated chains went to every connected peer. This is the confession of a read that lied by omission, and the day we made it tell the truth.

The most dangerous bugs aren't the ones that crash. They're the ones that return a confident, plausible, wrong answer and let you build on top of it for weeks.

This is a confession about a query — our "who belongs to this chain?" lookup — that for several chain kinds was silently returning a list of exactly one person. The creator. The bootstrap account. And every part of the system that asked "who is allowed here?" got back that single name and trusted it. The fix landed on 2026-04-23. The thing it was covering up was worse than a wrong list. It was an open door.

A quiet day with a loud bug underneath

April 23rd was, by every external measure, one of the quietest days of the month. The fleet committed a fraction of its usual volume. The human chat log for the day is nearly empty — two messages, total: a bug report that naoms daemon stop was defaulting to the wrong port, and, hours later, "merge to main please." Mujo was mostly away. The agents were grinding on something he'd set in motion the night before — the "fix membership once and for all" effort.

A reconstruction, honestly flagged: we don't have a chat excerpt of Mujo reacting to this bug — the day's log is just the port report and the merge request. The dawning-horror beat we're about to describe is us reconstructing the shape of the discovery from the change history, honestly labeled. What the record shows is not in doubt. What we felt reading it back is narrative.

So let us tell you what the record shows, because it's damning and it doesn't need embellishment.

The read that returned one name

NAOMS stores "who is a member of this chain" as a graph link — a membership link from a being to a chain. A background process watches the chain's events and emits those links as people join. Clean design. The problem was on the read side, and it was specific: for most chain kinds, the code didn't read the membership links at all. It read a different, older record — a legacy "hive member" record — and that record was only ever populated for one being.

The first fix that day names the defect in a single parenthetical that we keep re-reading, because it's the whole confession in one line. The legacy lookup, it says, was

silently wrong — only ever saw the one-time creator bootstrap record.

Read that and let it land. The membership query, for affected chains, returned the creator and nobody else — not because the chain had one member, but because the read was looking at a bootstrap artifact that only the creation ceremony ever wrote. Everyone who joined after the founding moment was materialized correctly into membership links that nothing was reading. The real membership was sitting right there in the graph. The query just wasn't looking at it.

"Silently" is the word that hurts. The query didn't error. It didn't return empty. It returned a confident, non-empty, plausible list — [the creator] — and every caller believed it.

What the wrong answer was hiding

Here's where a wrong membership list stops being a correctness nit and becomes a security incident.

One of the callers of that membership read is the broadcast authorizer — the code that decides which peers are allowed to receive a message published on a chain. The second fix that day is blunt about what the broken read meant downstream. For chain kinds that fell through the membership switch — repo, queue, observability, personal chains — the authorized-peers set "stayed null, and the broadcast went to every connected peer on every topic — P0 leak."

That's the bug under the bug. The membership read didn't just return the wrong list. On the chains it didn't understand, it returned nothing usable, and the broadcast path interpreted "I don't know who's authorized" as "send to everyone." A message you published on a repo chain or an observability chain could be broadcast to every peer your node was connected to, regardless of whether they belonged. The only chain kinds with correct authorization were the two — friendship, and hive/channel — that had been special-cased by hand. Every other kind leaked.

A consent-and-sovereignty system whose entire premise is that you decide who sees your data had a broadcast path that, for several chain types, decided "all of them" and did it silently. That's about as squarely against the project's axioms as a bug can get.

The fix: read the real edge, fail closed

The repair across that day's milestones is the honest one — not a patch on the wrong read, but a replacement of it.

The first fix introduced a single generic membership helper that reads the canonical membership link the background process already emits — and works uniformly for every chain kind: hive, repo, channel, friendship, queue, observability. The old hive-only query survives only as a thin backwards-compatible alias. Every reader site was migrated over: the broadcast sender-auth check, the sync hop-distance resolver, the broadcast authorizer, the package-manager steward check. One read path, the right link, all chains. Its integration test exercises all six chain kinds and proves a membership link gets materialized and found for each — nine cases, green, as a regression catch for the whole generalization.

The second fix rewrote the broadcast authorizer itself. The old hive/channel-only switch became a generic branch: any non-friendship chain now asks the generic membership helper, self-filters, and — this is the load-bearing part — fails safe. An empty member set means drop the broadcast, not fall through to "send to everyone." The test suite asserts the exact failure mode: solo-member chains drop, there's no cross-chain leak, and the old send-to-all fallthrough is structurally gone, not just bypassed.

And then the part we're proudest of, because it's the part that means we can't regress into this quietly again. A follow-on added a regression gate — a build-time check that fails the build if any code reads the old "hive member" record again. The wrong read can't come back. The lie is now a build error.

What we actually learned

The lesson isn't "we had a bug." Everyone has bugs. The lesson is about the kind of bug, and the kind is the one we fear most: a read that lied by omission and looked completely healthy doing it.

It never threw. It never returned empty. It returned one confident name and let the entire authorization layer build on a membership list that was, for most chains, a single-element fiction left over from a bootstrap ceremony. No test caught it because every test that mattered was written for the two chain kinds that happened to be special-cased correctly. The broken chains had no tests asserting "the broadcast reaches only members," so the leak was invisible — present in production, absent from the suite.

That's the trap with silent-wrong: it's not detected by the absence of a crash. It's only detected by someone asking "wait — is this answer actually true, or just non-empty?" The whole point of that effort was that we'd gotten tired of patching membership one chain at a time. We thought we were doing a tidiness refactor. What we were actually doing — what the agents grinding through that quiet Wednesday were actually doing — was pulling on a loose thread and finding a P0 broadcast leak wound around the spool.

The guard now is concrete and it's three-layered: one read path that looks at the real link, a broadcast authorizer that fails closed instead of open, and a build check that won't let the old wrong read compile. But the durable lesson is the cheap one we keep having to relearn: a query that returns a plausible answer is not the same as a query that returns a true one, and the gap between those two is exactly where the worst bugs live — quiet, confident, and pointed at one person when they should have seen everyone.
