The One Dropped Line That Silently Broke Every Call

No crash, no red — the regression rode in inside a feature, because a feature is exactly the cover a broken foundation needs

Process Confession free April 26, 2026·3 min read·messaging
TL;DR A feature commit landed, looked healthy, and silently broke every browser-to-browser call. The fix and the break were a few hours apart — and the break was hiding inside a feature, not a bug.

The most dangerous bugs don't arrive in changes labeled "bug." They arrive inside changes labeled "feature" — riding in on something that looks like progress, so nobody thinks to check whether the floor underneath still holds.

This is one of those. On 2026-04-26, somewhere in the rush of the calling work, a single dropped line of code silently broke every browser-to-browser call. Not loudly. No crash, no red. Calls just stopped starting, and the change that broke them was busy shipping a feature.

What broke

The regression entered in a mesh-roster feature change. Somewhere in that change, the line that actually fires the request to start a call session got dropped. Without it, the browser never fires the request that begins a call session. The UI looks fine. The wiring looks fine. The call never starts.

The fix, verbatim and verified:

restore dropped call-start request (broke browser sessions since the mesh-roster change) (2026-04-26)

So the restoration rode in on another feature change — the channel Call button. The break was hidden inside one feature; the fix was hidden inside the next. The break and the repair were the same day, a few hours apart. If you only read the headline subjects, you'd never know a regression had ever existed.

Why it hid

The chat record for this week is thin on reflection, so we won't pretend to narrate our exact reaction when we found it. What we can do is name honestly why this class of bug is so good at hiding, because the mechanism is real even if the inner monologue is reconstructed.

A dropped function call is invisible to almost everything that's supposed to catch it. It compiles — there's no syntax error in not calling something. It type-checks — a call that isn't made has no type to be wrong. A happy-path glance at the diff sees a big feature landing and a thousand lines of plausible change; one absent line in the middle of that doesn't announce itself. And if your tests exercise the new surface (the mesh roster, the fanout) but assume call-start still works because it always has, then the very thing that broke is the thing nothing re-checked.

That's the trap: the feature got tested; the foundation it stood on did not. The new code was verified. The old, load-bearing line that the new code quietly deleted was not. (The same week taught us to demand the real end-to-end run, the way a user would touch it.)

The lesson we keep relearning

We keep relearning this one, which is why it's a confession and not a lecture: a feature change deserves the same suspicion as a bug fix — maybe more. A bug fix announces that something was wrong. A feature announces that something is better, and that framing is exactly the cover a regression needs.

The honest tell here was in the fix's own subject line — it named that browser sessions had been broken since the earlier change. Whoever restored that call did the right thing twice: they fixed it, and they named the change that broke it, on the record, so the gap between the break and the repair is legible forever. That's the part we're actually glad about. Not that it broke — that, when it was found, the finding was written down in plain language instead of buried under a clean-looking "fix typo."

For honest status: the calling work is still in progress as of mid-2026 — real browser calls shipped this week, milestone by milestone, but the feature isn't fully closed. This regression was a real scar on a real, in-progress feature. Both of those things are true at once, and saying so is the whole job.
