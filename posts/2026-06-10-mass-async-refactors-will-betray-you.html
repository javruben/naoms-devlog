Mass Async Refactors Will Betray You

A green type-check on an 800-site sync-to-async conversion hid a live auth bypass and a broken friendship handshake. Here's the rule we built to catch it.

Process Confession free June 10, 2026·4 min read·test-discipline
TL;DR If you've ever shipped a big sync-to-async refactor on a green type-check and felt safe, this is for you. We converted ~800 call sites, the type-checker passed, and we believed it — but it can't see a missing await that reads false, prints "[object Promise]", or yields at the wrong moment and breaks a critical section. Here's what bit us, and the linter we built to catch it.

There is a particular flavor of confidence that a large refactor gives you, and it is almost entirely false. You convert hundreds of call sites from synchronous to asynchronous. The type-checker runs. It is green. Every signature lines up, every Promise<T> flows into something that expects a Promise<T>. You ship it believing the green meant what green usually means.

It did not. A passing type-check on an 800-site sync-to-async conversion is one of the most dangerous green lights we know, because the three ways this refactor actually fails are all invisible to the type system.

The three betrayals the compiler can't see

When you forget an await, you don't get a value of the wrong type that the checker rejects. You get a Promise, and a Promise is a perfectly good object that does perfectly wrong things depending on where you dropped it:

  1. In a condition, it reads true. if (!asyncFn()) — a pending Promise is truthy, so !Promise is always false. A security gate that was supposed to ask "is this allowed?" now silently answers "yes," forever, and type-checks clean.

  2. In a string, it stringifies. A forgotten await flowing into a WebSocket response or a template literal renders the literal text "[object Promise]". The types are fine. The wire is garbage.

  3. In the wrong place, it yields. This is the cruelest one, because the await is present and correct — and still wrong. Adding await introduces a yield point, and a yield point can shatter an implicit critical section that the synchronous code relied on without ever naming.

The third one is the one that actually bit us this week, and it's worth telling in full because it is so easy to do and so hard to see.

The friendship verifier that yielded at the worst moment

On 2026-06-10 we migrated the friendship verifier and the membership enrichers from a synchronous graph read to an async one — exactly the kind of mechanical, signature-preserving change that the conversion was full of. It type-checked. It looked obviously correct.

It was not. The commit message of the revert says it more precisely than we could reconstruct: the await introduced a materialize-ordering yield that breaks the implicit critical-section the pre-phase verifier relied on. In plain terms: on the peer-pair connect path, one peer's friendship.connected now got verified before the handshake node had materialized, because the new await handed control away at exactly the wrong instant. The verifier hard-aborted. The friendship chain never converged. Two peers that should have become friends simply… didn't, and nothing threw.

A separate bisect pinned it to that single commit. We reverted it the next day (2026-06-11). The synchronous version had an implicit guarantee — "this read completes before anything else runs" — that no type, no test, and no signature ever wrote down. The async version was correct in every way the tools could check and broken in the one way they couldn't.

The fix: teach the compiler to see the missing await

The honest response to "the type-checker can't see this" is not "be more careful." Careful does not survive 800 sites. The response is to build a tool that can see it. So this week we shipped a static-analysis rule that reads the syntax tree and flags a missing await — landed 2026-06-10, scoped first to the transport and gossip paths where a floating Promise is most lethal.

It immediately earned its existence. Going through its findings, we separated the roughly twelve intentional fire-and-forget calls (which got documented inline suppressions, not silent ignores) from the real bugs — and among the real bugs was a floating await on a domain key-access revoke-and-regrant during key rotation. And, as recorded across the week's audit, the same class of detector surfaced a live authorization bypass already sitting on the main branch — a gate that, because of a dropped await, had been reading "allowed" for everyone.

The lesson we'd tattoo on the next refactor

A mass sync-to-async conversion is not a type-safe operation, no matter what the type-checker tells you. The failure modes route around the type system entirely: truthiness, stringification, and — the assassin — yield-point reordering of critical sections that were only ever implicit. A green type-check on a refactor like this means "the shapes line up," and the shapes are not the danger.

So: never trust a mass async conversion on type-check alone. You need a missing- await linter that reads the use of the value, not just its type, and you need per-subsystem end-to-end tests on the critical paths, because the bug that yields at the wrong moment will only show up when two real peers try to become friends and quietly fail to.

We'll be honest about the state of it: the refactor is still being aligned, the conversion is real but the tail keeps regressing things, and we are clearly not done paying for it. That's the shape of the truth. The refactor that type-checks is not the refactor that works — it's just the one that lets you believe it does for a few hours longer.
