Everything Is a Package

How NAOMS features declare what they do, what they may touch, and get loaded at boot

Technology Architect free November 14, 2026·4 min read
TL;DR Beyond a small boot-critical core, every NAOMS feature is a self-contained package that declares its capabilities in a manifest. The loader reads those declarations, wires the package in, and hands its code a context that can only do what the manifest said.

Most of NAOMS isn't the kernel. Past a small boot-critical core (identity, consent, and the chain router), every feature is a self-contained package. The repository holds well over a hundred of them, and they all load the same way third-party plugins do. There is no privileged "built-in" tier, and even the package manager is itself a package.

This post explains how a package declares itself, how the loader brings it up, and why the capability model is built the way it is.

The manifest is the contract

Each package has a manifest that states, explicitly, what it provides:

  • the chain event types it owns (the prefixes it's allowed to write),
  • the graph node types it reads and materializes,
  • the messages it accepts from the browser or other clients,
  • its callable operations, which become both an API for the UI and tools for AI clients,
  • any scheduled jobs, its dependencies, its declared assets, and its UI.

The loader doesn't infer any of this from file names. The decision is manifest-driven, not convention-driven: if a capability isn't declared, it doesn't exist as far as the system is concerned. The manifest also drives routing. Declared event types become chain routes, and declared operations generate the API and tool surfaces.

A package is meant to be complete in itself: the manifest, the code that reacts to chain events, the code that projects those events into the graph, handlers, tests, and a UI micro-app. You can read one directory and understand one capability. That is the Wholeness axiom applied to code organisation.

Boot: discover, order, wire

At startup, the loader walks the set of packages. It sorts them by their declared dependencies, so a package loads after the ones it needs. Then for each package it:

  1. builds a scoped context for that package,
  2. runs its registration step,
  3. registers its chain, message, graph, and ontology declarations,
  4. hands its handlers to the dispatcher.

Each built-in package also records itself as installed through a signed chain event, so installation is part of the auditable history instead of an ad-hoc write. Third-party plugins go through a separate install path.

A few things load before the loader exists: identity, key, device, credential, and governance routes. They are registered up front because everything else depends on them.

Capabilities that fail closed

The context a handler receives is frozen and scoped. It has four rings, and each is gated by something the manifest declared:

  1. API calls, gated by the declared operations. A denied call returns an error.
  2. Sending messages to clients, gated by the declared message types.
  3. Graph queries and chain appends, gated by the declared node types and event types.
  4. Operational tables, gated by an explicit list and denied by default.

Defaults are closed. A package that declares no graph types gets no read access, and a package that declares no protocols can't send to peers. Handlers also never receive a raw database handle. This is the Honesty axiom at the code level: a manifest has to truthfully say what the package does, because the runtime holds it to that.

Keeping the boundary honest

Two directions of import are constrained. The core must not statically import from packages. Packages register into the core's extension points instead. Plugins reach the core only through a declared family of named import specifiers, never by relative path out of their own directory. Between packages, the rule is type-only imports of a sibling's public entry point, with runtime coupling going through the context.

The design doc is honest about the current state. The core-to-package rule is stated and a checker exists, but the checker isn't yet wired into commit or CI gates, and about eighty violations remain to refactor. Some of the cross-package rules are currently warnings, not hard failures.

Signed distribution and sandboxed UI

For distribution builds, each package gets a signed sidecar file that pins a hash of its static import graph and declared assets, plus hashes of the lockfiles. Signing comes from the release key ceremony, and a locally re-hashed sidecar isn't accepted without re-signing. That makes a package's boundary a verifiable fact, and the design is modelled on signed extension distribution in browsers and on Nix-style content-addressed builds. A source checkout has no sidecar, and the daemon itself doesn't verify plugin integrity at boot. Enforcement happens on distribution builds.

Package UIs run in sandboxed frames that talk to the daemon only through a message-passing API. They never touch it directly.

The metaphor

The project's own framing is that the kernel is the brain and packages are the senses. The system keeps working without any single package, and packages extend what it can perceive and do. The other inspirations the doc names are Unix (one package, one job), Erlang's supervision trees (dependency-ordered boot), and browser extension manifests.
