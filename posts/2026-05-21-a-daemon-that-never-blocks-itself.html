A Daemon That Never Blocks Itself

Why a single event loop is always one un-yielding call away from freezing every client at once — and the invariant that holds the line

Technology Architect paid · premium preview May 21, 2026·7 min read·agentic-fleet
TL;DR The local process every client talks to runs on a single event loop — and one synchronous call that won't yield can freeze everyone at once. This week's most-worked promise was the unglamorous one that it never does: when this daemon is slow, it's the machine that's busy, never the daemon fighting itself.

The week's most-worked theme wasn't a feature you can screenshot. It was an invariant — a property the system must hold no matter what — and it earned more commits than anything else on the board. The invariant, stated exactly as the roadmap item states it:

"the daemon is bounded only by system resources, never by its own JS thread(s)." — the roadmap item that drove the week's work

That sentence is doing more work than it looks like. Let us unpack why an experienced engineer should read it and immediately tense up a little, and what it cost to make it true.

The shape of the problem: one loop, many masters

The NAOMS daemon is the local process every client talks to. The TUI talks to it. The browser surface talks to it over WebSocket. The CLI talks to it. Other daemons — peers — talk to it. It is the single point through which identity, encryption, chain operations, and peer sync all flow. And at its heart it runs on an event loop.

Event-loop concurrency is a wonderful model right up until the moment it isn't. Its entire premise is cooperative: every task promises to yield quickly so the loop can service the next one. Thousands of in-flight operations interleave smoothly because none of them hogs the thread. The model has exactly one catastrophic failure mode, and it's the one every event-loop system shares: a single synchronous operation that doesn't yield freezes everything. Not the slow operation — everything. Every connected client, every peer, every pending request, all stalled behind one call that decided to do its work without giving the loop a turn.

Now layer in what this daemon actually does. It isn't shuffling JSON. It does cryptographic work. It calls into native Rust over FFI for the heavy lifting — signing, lattice operations, blob hashing. It appends to a chain. Any one of those is a candidate to be the synchronous call that eats the thread. A bulk import that signs ten thousand entries. An FFI call that blocks while native code grinds. A chain append that does its work inline. Each is a loaded gun pointed at the event loop, and the trigger is the word synchronous.

So "bounded only by system resources, never by its own JS thread" is not a vague aspiration. It's a precise contract: the daemon may be slow because the CPU is busy or the disk is full — those are honest, system-level limits — but it must never be slow because one of its own operations refused to yield the loop. The bottleneck must always be the machine, never the daemon's own single thread blocking on itself.

Why this is existential for a fleet client

Here's the part that makes this invariant non-optional rather than nice-to-have.

If this were a single-user desktop app, a momentary freeze is an annoyance — the spinner hangs, you wait, it recovers. But this daemon is the local hub for an agent fleet and a multi-surface client. When the thread blocks, it doesn't degrade one user's experience. It blocks the WebSocket isolate serving the browser surface, the control plane, the peer connections, and every agent operation in flight — simultaneously, because they all live behind the same loop. One un-yielding FFI call doesn't slow the daemon down. It takes the daemon offline, for everyone, until it returns.

That's why this became the highest-commit theme of the week. It's not glamorous, but it's load-bearing in the most literal sense: every other feature is only as available as the loop that serves it. An identity system that freezes is not a more secure identity system. It's a down one.

What "never blocks itself" looked like in code

The marquee landing in the week was the daemon-state and control-plane work — a production daemon-state subsystem, a control-plane channel over a Unix-domain socket, and a clean restart path. Three pieces, each in service of the invariant:

A production daemon-state subsystem. To guarantee the loop is never blocked, you first need to be able to observe the daemon's liveness without going through the very loop that might be blocked. A daemon-state subsystem is the foundation for asking "is this thing actually responsive right now?" as a first-class, queryable fact rather than an inference.

Control-plane UDS endpoints. A Unix-domain-socket control plane is a deliberate architectural choice here, and it's the right one. It gives you a channel to the daemon that is separate from the main request path — a side door for control operations (status, restart) that doesn't have to queue behind whatever the loop is currently doing. If your only way to ask a daemon how it's doing is through the same congested front door as everything else, you can't manage it when it's struggling. The control plane is the management channel that stays reachable.

A real restart story (DX). And the honest acknowledgment baked into the same commit: sometimes the right answer to a wedged process is a clean, fast restart, and that has to be a first-class developer-experience path, not a kill-and-pray. Building restart in is an admission that even with the invariant held, the operational reality of a long-running daemon includes "turn it off and on again, cleanly" — and that path deserves to be engineered, not improvised.

We want to be precise about status, because honesty about partial work is one of our rules: this one genuinely shipped. It is one of the week's real, completed wins, not an in-progress claim. The invariant isn't a goal we're chasing; it's a property we landed and gated.

The deeper pattern: honest limits vs dishonest ones

There's a principle under this invariant that generalizes beyond daemons, and it's worth stating plainly because it connects to how NAOMS thinks about everything.

There are two kinds of limit a system can hit. Honest limits come from physical reality: the CPU is saturated, the disk is full, the network is down, there are genuinely more requests than there is hardware to serve them. Those limits are true — the system is telling you something real about the world, and the right response is more hardware or less load. Dishonest limits come from the system's own structure: it's slow not because the machine is busy but because the system fought itself, blocked its own thread, serialized something that didn't need serializing. A dishonest limit is the system lying about how much it can do — pretending the machine is the bottleneck when the bottleneck is its own architecture.

"Bounded only by system resources, never by its own JS thread" is a commitment to only ever hitting honest limits. When this daemon is slow, the slowness should always point at something true — the CPU, the disk, the network — and never at a self-inflicted wound in the event loop. That's a Wholeness-flavored idea: a whole component's performance is governed by its real environment, not by an internal flaw it has to apologize for.

A footnote from the same day, on honest limits

It's fitting that the day we're dating this piece to — 2026-05-21 — had its own small lesson in honest versus dishonest limits, on the infrastructure side rather than the daemon side. From the day's chat:

"something went wrong. the wireguard tunnel stopped working. investigate" — owner message, 2026-05-21T15:25Z

"yes now it works again" — owner message, 2026-05-21T15:29Z

A four-minute network outage between hosts in the mesh. That's an honest limit — the network was genuinely down, the system was genuinely unreachable, and the fix was to restore the tunnel, not to paper over it in software. It's the same distinction the daemon invariant draws, just one layer down the stack: when something is slow or unreachable, the discipline is to find out whether the limit is real (fix the world) or self-inflicted (fix the code), and never to let a self-inflicted limit masquerade as a real one. A daemon that blocks its own thread is software pretending the machine is busy. The honest engineering move is to make sure that lie is never available.

The least screenshot-able theme of the week was also its most foundational. Every visible feature NAOMS ships rides on a single event loop, and a single event loop is always one un-yielding call away from taking everyone down at once. The week's most-worked invariant was the unglamorous promise that it won't: that when this daemon is bounded, it's bounded by the machine telling the truth about its limits — never by the daemon lying to itself about its own.
