Why the Map Keeps Only 32 Tile Helpers in Memory

Each map channel gets one ready-made helper that is reused for every tile, and the oldest unused helper is let go once there are more than 32

Technology Architect free November 23, 2026·4 min read
TL;DR When the NAOMS map draws tiles from a hive channel, it keeps a ready-made helper per channel so it does not redo slow setup work on every tile. This week that set of helpers got a ceiling: at most 32, with the least recently used one dropped first and simply rebuilt if it is needed again.

The NAOMS map draws its picture from tiles, small squares of the world, and it can stream those tiles from a channel in your hive instead of from a commercial map server. We wrote about that in One Map Everywhere and A Map Whose Pins Live on Nobody's Server. This post is about one small piece behind it: how NAOMS remembers the work it did to reach a channel, and why that memory now has a fixed size.

One helper per channel, built once

Before the first tile from a hive channel can be shown, NAOMS has to do some setup. It finds the channel and checks that you are allowed to read from it. That takes a walk through your hive's records, which is far too slow to repeat for every tile of every frame while you pan.

So NAOMS does the setup once and keeps the result as a ready-made helper. Every later tile from the same channel goes through that helper. There are two kinds of tile, picture tiles and the newer vector tiles that are drawn from shapes, and each kind has its own set of helpers.

A screen can ask for tiles from a particular channel by name. A helper is built for one channel only, so NAOMS keeps one helper for each channel that has been asked for. Reusing one helper for everything would hand a request for one channel the helper built for another.

The problem with "keep everything"

Until this week, those helpers were kept in a list that only ever grew. Normally that is fine, because a normal map asks for one or two channels. But the channel name comes in with each request. A screen or a tool that asks for many different names, by mistake or by looping over a list, would add a new helper for every one of them, and none would ever go away. The NAOMS program on your machine would slowly use more and more memory for helpers nobody needs any more.

The fix: keep the 32 most recently used

Both sets of helpers, picture and vector, now hold at most 32 each. The rule is the usual "least recently used" one:

  • When a helper is used, it moves to the front of the queue.
  • When a new helper is added and there are now more than 32, the one at the back, the one that has gone unused the longest, is let go.
  • If a helper that was let go is needed again, NAOMS simply builds it again on the next request. Building is safe to repeat. The only cost is doing the setup walk once more.

One detail matters here. Sometimes a helper cannot be built because its setup fails. NAOMS remembers that outcome too, and the map carries on with its bundled world map and the tiles already cached on your device. That remembered "not available" counts as a normal entry. It is kept and reused like any other, so NAOMS does not retry the failing setup on every tile, and it is let go by the same rule.

How we checked it

The change comes with a pair of tests, one showing it works and one showing that a broken version fails. One test asks for ten times 32 different channel names and checks that the store stays at exactly 32, that the oldest names were let go and the newest kept. Others check that a helper still in use survives while newer ones push the oldest out, that asking for the same channel many times counts it once, that a remembered "not available" is reused rather than retried, and that both the picture and the vector helpers use the bounded store. To prove the tests can actually catch a mistake, we ran them against two deliberately broken copies of the code. In one, the step that lets old helpers go was deleted. In the other, the vector helpers went back to the old list that only grows. The tests failed on both broken copies and passed on the real one.

What you notice

Nothing, which is the point. A map that uses a handful of channels behaves exactly as before, because 32 is far more than one screen needs. A loop that asks for hundreds of names now costs a fixed, small amount of memory instead of an ever-growing one.
