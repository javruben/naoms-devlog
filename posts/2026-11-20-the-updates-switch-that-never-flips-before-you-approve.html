The Updates Switch That Never Flips Before You Approve

Turning automatic updates on or off is a decision about your own machine, so NAOMS shows what is stored, waits for your approval, and says 'unreliable' rather than guess

Product Architect free November 20, 2026·4 min read
TL;DR The Software updates switch in Configuration is a thin window over one stored choice. This is how it reads that choice honestly, why it will not move until you approve, why a failed read shows neither on nor off, and why a build that cannot be trusted to update itself says so plainly.

An automatic update replaces the app that is running, and it can do that while you are not looking. That is a lot of authority to hand to a toggle, so the toggle in NAOMS has to be more careful than most. You will find it under Configuration, in the Software updates section, in a panel called Automatic updates. This is what it does, and why it behaves the way it does.

One stored choice, three honest states

Behind the switch is a single stored setting: do you allow updates that reach this device to install without asking? NAOMS reads it from your own record, the same place the background update job reads it. There is only one reader. The switch does not keep its own opinion.

If nothing has ever been recorded, updates are off, and each one asks before installing. If you have chosen, the switch shows your choice. And there is a third state that most switches do not have: Unreliable.

Unreliable means the stored setting could not be read as one clear value. Maybe the read failed. Maybe several conflicting copies of the setting turned up. In that case the switch is dimmed, its position is neither on nor off, and the words say that no guess is being shown.

The reason is simple. A switch that guesses "off" when it does not know could tell you updates are safe while they are not. A switch that guesses "on" could do the reverse. Showing the doubt is the only answer that cannot mislead you. The background job follows the same rule from its side: when the setting is unreadable or the copies disagree, it leans toward not installing. The one exception is when every copy of an ambiguous setting says on. The panel words that case plainly rather than hiding it.

The switch waits for you

Pressing the switch does not change anything on its own. It sends a request, and that request is held until you approve it in the normal approval place.

While it waits, the switch stays exactly where it was and says something like: turning on, waiting for your approval, nothing changes until you approve. It does not slide over first and apologise later. The position you see is always the stored state, never a hope.

When the answer comes back, the switch does not take it on trust either. It reads the stored choice again and draws that. If the approval was declined, you see a short note that nothing changed. If no receipt came back, it says the change was not confirmed. If the approval is simply still open, it tells you so, and that what you see is what is stored. An approval can sit for minutes while you are elsewhere, and the switch waits for it.

One writer, not two

Turning updates on or off from the command line and from the panel do the same thing, by the same route. The change is built in one place and sent unchanged. The panel builds nothing of its own. That matters because a setting that two different pieces of code can write is a setting that can drift into saying two different things.

The write also replaces the old choice instead of piling up beside it. Turning updates off after having turned them on leaves one stored answer, the latest one, not two answers in some arbitrary order. Anything that is not a plain yes or no is refused outright rather than rounded to the nearest meaning, because a consent value that arrives as the wrong kind of thing could otherwise be stored as a choice you never made, or read back as the opposite of what you asked for.

When the build itself says no

There is one more thing the panel will tell you. Some builds are signed with a release key that this build cannot vouch for: one that has been retired, or one that could not be read. A build like that never installs updates on its own, whatever the switch says. The check runs before anything is fetched or staged, and it applies only to unattended updates. If you are at the keyboard and choose to apply an update yourself, nothing changes.

So on such a build the panel says "Off on this build" and tells you to install updates by hand. If the stored switch happens to be on, it says that too: the setting is stored, but it has no effect here. The stored value is left as it is, because that is what you chose. What the panel changes is what it tells you the choice is worth.

What this buys you

A choice about code that rewrites your own machine should have these properties, and the switch has all of them:

  • It shows what is stored, not what it wishes were stored.
  • It says "I cannot tell" when it cannot tell.
  • It does not move until you approve.
  • It reads the result back, so the picture you end up with is the real one.
  • It will not promise an automatic update that the build is not going to perform.

None of it is visible when everything works. A switch you can flip, and a note when you cannot. The care is all in the cases where something else would have guessed.
