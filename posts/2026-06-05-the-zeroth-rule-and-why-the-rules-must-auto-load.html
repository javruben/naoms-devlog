The Most Important Rule Is the One That Arrives First

How a hundred AI agents share one repository without destroying each other's work — and why the rule that makes it possible has to load itself

Process Journal free June 5, 2026·5 min read·agentic-fleet
TL;DR When a hundred AI coding sessions share one repository, one rule keeps them from overwriting each other — and it only works if it reaches every session before any work starts. The lesson: an instruction that has to be fetched is a suggestion, and on a long enough timeline it gets skipped on the day it mattered most.

Some rules are interesting. One is load-bearing. This is about the load-bearing one, and about the humbler question of how it reaches the people — and the machines — who have to follow it.

How the rules are supposed to work

NAOMS isn't built by one person at a keyboard. It's built by a fleet of AI coding sessions running concurrently against the same repository — not a dozen, as some stale documentation of ours claimed, but "we often get to 100 concurrent."

A hundred sessions editing one shared copy of a codebase would be chaos, so they don't. Each session works in its own worktree: an isolated checkout of the same repository, its own directory with its own branch, sharing the project's history but not its working files. A session edits only inside its worktree, and its changes reach everyone else through a single serialized merge path rather than by landing directly in the shared copy.

That is the Zero Rule, the one that comes before all the others: work in a worktree; never edit a file in the shared main working tree. It sounds like housekeeping. It is the rule that keeps the whole arrangement from eating itself.

Consider what happens without it. If even a handful of sessions edit the shared tree directly, they race each other: one session's edit lands on top of another's half-finished change; a third session looks at the state of the tree, sees modifications it did not make, and reacts to a situation nobody intended; work gets silently destroyed in the churn. Get this rule wrong and the cost isn't a bug — the cost is other sessions' work, gone. That's why it's zeroth rather than fourteenth. Not the most interesting rule. The most load-bearing one.

A rule like that is only worth as much as its delivery. So the second half of the design is about arrival: the project keeps its operating rules in a single canonical file at the repository root, following the open AGENTS.md convention that several agent tools now read, and that file is auto-loaded — placed in front of every session before it does any work, without the session having to know it exists or think to ask for it.

That property is what makes it a rule at all. An instruction you have to remember to load is not a rule; it's a suggestion that applies on the days you happen to read it. And it has a corollary about agent memory: if the authoritative source loads itself every time, you don't need a pile of accumulated reminders compensating for it. One file, always present, and the memory can simply point at it.

What was wrong

We asked the same question twice in three days, and the fact that we had to ask it the second time is the whole point of this piece.

The first time, on the third of June, it was almost casual:

"what is the zeroth rule?"

And then, when the agent fumbled it:

"read agents.md"

The instinct at that moment was to be annoyed at the agent. By the fifth of June we'd asked the better question:

"why did you not find the zeroth rule? is it not in ~/dev/naoms/agents.md?"

It was. It was right there, written plainly. The agent hadn't forgotten it out of carelessness — it had never read it, because the file wasn't the one being loaded automatically:

"why isnt agents.md auto loaded? is that a claude code change? is claude.md still auto loaded? is claude.md still symlinked?"

The conventions had drifted apart. The canonical rules lived in the root file described above; the harness in use auto-loaded a differently-named one. So the project's most important instruction sat in a file an agent had to be told to open, rather than one it always saw. Nothing in the code was broken. The rule was correct. The agent was capable. The only flaw was a loading convention — which file shows up before work begins — and that one quiet gap was enough to let the single most consequential rule in the project go unread.

How it was fixed, and what it left us asking

The mechanical fix is boring: make the canonical rules file the one that auto-loads. The file the harness expects by name, CLAUDE.md, is an ordinary one-line file whose entire contents are an import directive — @AGENTS.md — so the file that gets loaded automatically pulls the canonical rules file in behind it. One line, done. The same one-liner sits next to each subtree's own rules, so a session working in that subtree gets those too.

The principle it taught is the part worth keeping, and it was said plainly that week:

"with this you can delete the stupid question memory and instead add a memory that says read agents.md in the repo root on how to work with me"

That is the agent-memory hygiene lesson landing. For a while we had been patching the agent's forgetfulness by stuffing answers into its long-term memory — a memo here, a reminder there, accreting like sediment. Wrong layer. You don't fix "the agent doesn't know the rules" by memorizing the rules one question at a time. You fix it by making the one authoritative source load itself, every time, before the agent does anything — and then you can delete the scattered patches, because they were only ever compensating for a file that wasn't being read.

What that one-line import does not fix is the class of failure, which is invisible by nature: a delivery gap leaves no trace in the code, no failing test, nothing to grep for. So the durable outcome isn't the import line. It's a question we now ask of every important rule we write: does this arrive on its own, or does it wait to be fetched? Because the rules that wait to be fetched are exactly the ones you'll wish had arrived on their own, on the one day someone forgets to go get them.
