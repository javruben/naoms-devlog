The Most Important Rule Is the One That Arrives First

The zeroth rule, and why the rules must auto-load

Process Journal free June 5, 2026·4 min read·agentic-fleet
TL;DR An AI agent forgot the one rule it could least afford to forget — and it turned out the safety rule was sitting in a file nothing loaded automatically. The lesson: if your most important instruction has to be fetched, then on a long enough timeline it gets skipped on exactly the day it mattered most.

There's a question we asked twice in three days, and the fact that we had to ask it the second time is the whole point of this piece.

The first time, on the third of June, it was almost casual:

"what is the zeroth rule?"

And then, when the agent fumbled it:

"read agents.md"

The zeroth rule, in NAOMS, is the one that comes before all the others — what we call the Zero Rule. It says: work in a worktree; never edit a tracked file in the main working tree. It sounds like housekeeping. It is, in fact, the single rule that keeps the whole thing from eating itself.

Why this rule and not another

Let us explain why it's zeroth and not just "rule fourteen."

NAOMS isn't built by one person at a keyboard. It's built by a fleet of AI agent sessions running concurrently — not a dozen, as we had to correct some stale documentation that week, but "we often get to 100 concurrent." A hundred sessions, all working on the same repository at the same time.

If even a handful of those sessions edit files directly in the shared main working tree, they race each other. One session's edit lands on top of another's half-finished change; a third session's git status sees a tree full of modifications it didn't make and panics; work gets silently destroyed in the churn. The worktree rule exists so that every session does its work in its own isolated copy — its own worktree — and only ever integrates through a single, serialized merge path. Get this rule wrong and the cost isn't a bug. The cost is other sessions' work, gone.

So it's not the most interesting rule. It's the most load-bearing one. And that's exactly why an agent forgetting it is so much worse than an agent forgetting, say, the preferred table width.

The real problem wasn't the agent

Here's where we had to be honest with ourselves. When the agent forgot the Zero Rule, the instinct was to be annoyed at the agent. But by the fifth of June we'd asked the better question:

"why did you not find the zeroth rule? is it not in ~/dev/naoms/agents.md?"

It was in agents.md. It was right there, written plainly. The agent didn't forget it because it was careless. It forgot it because it had never read it. And it had never read it because the file wasn't being loaded automatically:

"why isnt agents.md auto loaded? is that a claude code change? is claude.md still auto loaded? is claude.md still symlinked?"

That string of questions is us working out a small but real piece of infrastructure in real time. The conventions had drifted. The repository carries its operating rules in a root AGENTS.md — following the open AGENTS.md convention that several agent tools now read. The harness in use auto-loaded a differently-named file. So the canonical rules file and the auto-loaded file had quietly come apart, and the most important instruction in the project was sitting in a file that the agent had to be told to open, rather than one it always saw.

An instruction you have to remember to load is not a rule. It's a suggestion that only applies on the days you happen to read it.

The fix is a philosophy, not a flag

The mechanical fix is boring: make the canonical rules file the one that auto-loads, via a symlink so the harness's expected name resolves to the real AGENTS.md. One file, one link, done.

But the principle it taught us is the part worth keeping, and it was said plainly that week:

"with this you can delete the stupid question memory and instead add a memory that says read agents.md in the repo root on how to work with me"

There's a hygiene lesson buried in there about agent memory. For a while we'd been patching the agent's forgetfulness by stuffing answers into its long-term memory — a memo here, a reminder there, accreting like sediment. That's the wrong layer. You don't fix "the agent doesn't know the rules" by memorizing the rules one Q&A at a time. You fix it by making the one authoritative source load itself, every time, before the agent does anything — and then you can delete all the scattered patches, because they were only ever compensating for a file that wasn't being read.

The most important instruction in a system has to be the one that arrives first, automatically, with zero chance of being skipped. If your safety-critical rule depends on someone — human or agent — remembering to go fetch it, then on a long enough timeline it will be skipped, and the day it's skipped is the day it mattered most.

What it left us thinking about

The thing we keep turning over is how invisible this class of failure is. Nothing was broken in the code. The rule was correct. The agent was capable. The only flaw was a loading convention — which file shows up before work begins — and that one quiet gap was enough to let the single most consequential rule in the project go unread.

It's a small story. An agent forgot something; a file wasn't auto-loaded; we fixed the symlink and deleted some memory cruft. But it sharpened a question we now ask of every important rule we write: does this arrive on its own, or does it wait to be fetched? Because the rules that wait to be fetched are exactly the ones you'll wish had arrived on their own, on the one day someone forgets to go get them.
