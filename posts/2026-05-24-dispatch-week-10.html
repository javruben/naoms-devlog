NAOMS engineering update · Week 10

Heavy work stopped freezing the screen, and 75 flat commands became 44 families

Two changes worth your time this week: the daemon stopped blocking on its own thread, so a bulk import or a replay no longer locks up the screen while it runs, and the command line was redesigned from about 75 flat commands into 44 noun-verb families. Everything else that moved is listed at the end.

Four things changed this week

One per major area, and a week with an unusual shape: 1,303 commits on the Monday, 100 on the Wednesday, 1,028 on the Saturday.

1

Your interface stays responsive while heavy work runs

The daemon no longer blocks on its own thread. It is bounded by your system's resources instead, and it has a clean restart path when it does need to come back.

2

Bulk seed, import and replay stopped freezing the screen

The native side now hands its work over in batches rather than stalling the main thread until the whole job is finished.

3

Pairing across your devices is caught by tests before it reaches you

Cross-device pairing runs on a shared helper that stands up two peers, so a regression in it is caught automatically rather than found by a person.

4

You can target an agent run by capability tier or by exact model

Two ways to ask for the same thing: name the class of machine you want, or name the specific model you mean.

A daemon that never blocks itself

The feature: the background service that does the work — importing, replaying, seeding — while you carry on using the interface in front of you.

Before: it blocked on its own thread, so heavy work and the screen shared one queue, and the screen lost. Now: it is bounded by your system's resources rather than by a single lane, and it has a clean restart path for the times it does have to come back. (A daemon that never blocks itself)

A single shared thread is a queue, and everything behind it is waiting. The symptom people report is "the app froze", but nothing was frozen — one long piece of work was holding the only lane, and every quick thing behind it inherited the long thing's duration.

What was built. The second half of the same problem was on the native side, where bulk work — seeding, importing, replaying — was carried out in one uninterrupted stretch. It is now appended in batches, so the main thread regains control between them and the screen keeps drawing.

Batching is the unglamorous fix and it is the right one. Making the long operation faster buys a smaller freeze rather than no freeze, and the freeze returns the first time someone imports twice as much. Handing the work over in pieces changes the shape of the problem instead of its size.

The clean restart path is the other half, and it is easy to undervalue. A service that never blocks can still need to come back, and a restart that loses its place is its own kind of freeze — the interface returns, and the work you were waiting on has to begin again from nothing.

What is still missing. No latency figure is quoted here. What changed is structural — one lane became many — and this report does not claim a measured improvement it did not measure.

One noun, one verb: 75 commands became 44 families

The feature: the command line — the way you ask NAOMS to do something without a screen in front of you.

Before: roughly 75 flat top-level commands, each named on its own terms, so finding the right one meant already knowing it existed. Now: 44 noun-verb families, where you name the thing and then what you want done to it. (One noun, one verb: cleaning up the NAOMS CLI)

A flat command list is a vocabulary test. Every flat name is a word you either know or do not, and there is no way to reason from one to the next. A noun-verb surface lets you guess: if you know the noun, you can try the verb you would expect, and be right more often than not.

The count matters less than the shape. Going from 75 to 44 is a regrouping rather than a cut: commands that were siblings by accident became siblings by subject. The ones with no subject at all had to acquire one before they could be placed anywhere.

Separating the design from the shipping is deliberate rather than a delay. A command surface is the part of a product people memorise, so changing it twice costs far more than changing it once — and the only way to change it once is to settle the whole shape before any of it moves.

What was built, and what was not. The design landed this week; shipping it is the next step. Until it does, the surface people actually type is still the flat one, and this report does not describe the new one as available.

What this means, in plain terms

Five general lessons this week's work paid for, each learned by getting something wrong somewhere first.

A single lane is a queue, whatever you call it

The daemon blocked on its own thread, so a long import and a screen redraw competed for one lane and the redraw waited. Users describe that as a freeze; the code describes it as correct sequencing. Any resource with one lane converts every long operation into a delay for everything unrelated behind it.

Hand bulk work over in pieces, not in one stretch

Seeding, importing and replaying used to run as one uninterrupted block. They are now appended in batches, so control returns between them. Making the block faster would only have shortened the freeze. Changing the shape of a long operation beats shortening it, because the shape survives the data getting bigger.

Give the same control a coarse form and an exact one

An agent run can now be targeted by capability tier — the class of machine you want — or by naming the exact model. Neither replaces the other: one is for when you care about the outcome, the other for when you are comparing. A control that offers only precision is unusable, and one that offers only convenience is untestable.

A behaviour between devices can only be tested between devices

Cross-device pairing now runs on a shared helper that stands up two peers, so regressions in it are caught automatically. Before that, the failure mode had no test that could see it, because it does not exist inside one peer. Some defects are properties of the gap between two things, and only an instrument that spans the gap can find them.

Do not publish a number you would have to defend with an excuse

No net line-count figure appears in this report. At roughly four thousand commits a week the diff is dominated by fixtures and generated catalogues, so a net figure would describe machine-written bytes and be read as human effort. A metric that needs a caveat longer than itself is not a metric; it is a claim with a disclaimer attached.

What would prove this week's responsiveness claim wrong

Four things this report has only half-proven, each stated as a commitment rather than as a task.

  • No latency figure stands behind "responsive". The change is structural: heavy work and the screen no longer share one lane. Until a measurement is published, the claim rests on the shape of the fix.

  • The command surface people type has not changed. 44 families exist as a design. Anyone using NAOMS this week still faces about 75 flat commands, and a redesign that does not ship is a document.

  • Pairing tests exist; their coverage is unstated. Two peers on a shared helper is enough to see the class of defect that lives between devices. This report does not say how much of pairing those tests actually exercise.

  • A weekly total is a poor description of this week. Monday ran 1,303 commits and Wednesday ran 100. Any conclusion drawn from the 4,107 figure alone is drawn from an average that never happened.
